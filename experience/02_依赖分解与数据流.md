# 02 依赖分解与数据流

> overlap 设计的第一步永远是依赖分析，不是写 kernel。这一步决定了重叠上限，后面所有调优都在这个上限之内。

## 1. 方法：先画 producer-consumer 图，再找独立维度

对目标算子画出 shared tensor 的生产-消费关系：

- TP：AllGather → GEMM（consumer 等 producer）；GEMM → ReduceScatter（producer 推 consumer）；AllReduce → RMSNorm/residual。
- MoE：dispatch → expert GEMM0（通信→计算）；expert GEMM1 → combine（计算→通信）；routing metadata → 一切布局。

然后对 shared tensor 逐维度问一个问题：**"沿这个维度切开后，一个分块的消费是否只依赖对应分块的生产？"**

- **是** → 该维度可分解，依赖从"等整个 tensor"降为"等一个分块"。
- **否** → 沿该维度切分不产生任何提前放行的机会，白付切分成本。

## 2. 各算子的正确分解维度（经过验证的结论）

| 算子 | 可分解维度 | 不可分解维度及原因 |
|---|---|---|
| AG + GEMM | M 维（输入行 = rank 分片） | K 维切 A 会引入部分和依赖 |
| GEMM + RS | M 维（输出行的目标 rank） | — |
| MoE dispatch + GEMM0 | M 维（token 行），且按 source rank 聚合 | **N 维不可**：沿 N 切的每个 tile 仍依赖全部 rank 的 token 到齐 |
| MoE GEMM1 + combine | **N 维**（输出列块） | **M 维不可**：combine 要对同一 token 的 topk 行归约，行与行强耦合（同一 token 的 topk 个 expert 输出散在多个 expert 问题里） |
| AllReduce + Norm | token/row 维（配合 RS+AG 分解） | 归约维本身 |
| attention 的 seq 切分 | sequence 维，但有 causal 顺序约束（后块要等前块 KV 写完） | — |

核心教训（Comet）：**同一个 MoE 层的两半，分解维度是相反的（layer0 沿 M、layer1 沿 N）**。分解维度由数据流决定，不存在"统一切法"。

## 3. readiness 粒度：把细粒度事件聚合成粗粒度信号

依赖分解到 tile 级不等于信号也要到 tile 级。成熟做法都在做"聚合"：

- **按 rank 聚合**（Comet layer0）：token 先按 (source_rank, expert) 排序，使每个 GEMM 子问题的依赖收敛为"某个 rank 的分片已到达"——一个 flag 放行一批 tile，信号数从 O(tiles) 降到 O(ranks)。**排序/重排是把不规则依赖变成规则依赖的通用手段**。
- **按 wave 聚合**（FlashOverlap）：一个 wave 内的 tile 近似同时完成，按 wave group 同步；信号 = 每段一个计数器。
- **计数聚合**（TileLink/Triton-distributed）：N 个 tile 各做一次 release 原子加，最后一个到达者负责发跨 rank 通知——细粒度完成事件在本地聚合，跨设备信号只有一次。
- **按 128 行 tile 聚合**（TK MoE dispatch）：每个到达 token 给所属行块计数器 +1，计数凑满一个 GEMM tile 的行数才放行计算。

判断标准：**信号粒度应该是"能触发一次有意义的下游动作"的最小单位**——一次高效通信的最小消息量、或一个 GEMM tile 的输入需求，而不是数据产生的自然粒度。

## 4. 重排（reorder/sort）的三条纪律

1. **重排必须免费或近似免费**：融进 producer 的写出地址（写到重排后的位置）或 consumer 的读入索引（gather），绝不引入独立的搬运 kernel。FlashOverlap 的 pre/post-reorder、Comet 的 gather/scatter 索引都是这个思路。
2. **重排本身要纳入流水**：MoE 的 token 排序、grouped GEMM 的 problem 重建是每步都要做的 CPU/GPU 开销（Comet 每步有 D2H 同步），小 batch 时可能吃掉收益；能缓存就缓存（DeepEP 的 handle 复用——路由不变时跳过全部 layout 计算）。
3. **消费端如果对顺序不敏感，就不要恢复顺序**：下游是 elementwise/归约类算子时，把逆重排融进它的读入即可；下游如果也是自己可控的 kernel，可以让重排"传染"下去，永不显式恢复。

## 5. 依赖分解阶段就要回答的检查单

- [ ] 每个分块的依赖集合是否**静态可算**（TP：仿射公式）还是**运行时才知道**（MoE：查找表）？后者需要为 metadata 的构建与传输单独设计流水。
- [ ] 一个计算 tile 是否会跨越多个通信分块的边界？（Flux：一个 GEMM tile 可跨 2 个 chunk，要逐 chunk 等待；Comet：跨 rank 边界的 tile 推迟到依赖的最晚 stage 处理。）边界 tile 的处理策略必须显式设计。
- [ ] 分解后是否存在"无需通信的本地块"？有——**本地块的调度位置是免费优化**：consumer-wait 型（AG）本地块最先算（零等待起步），producer-push 型（RS）本地块最后算（尾部无暴露通信）。
- [ ] 依赖必须等完整 tensor 的部分（如归约维）是否可以用两级分解绕开（先本地归约再跨设备）？
- [ ] 中间的 layout transform 是否已融合？若不能融合，它会成为新的串行阶段。

## 6. 思想级伪代码：依赖分解的产物

一次成功的依赖分解，输出物应当是四个映射（TileLink 的抽象，值得作为设计文档的标准格式）：

```text
shape 映射:   分块 id -> 它覆盖的数据切片（行/列范围）
rank 映射:    分块 id -> 数据所属/所去的设备
channel 映射: 分块 id -> 它使用的信号槽位/通信通道
顺序映射:     分块 id -> 它在计算/通信中的调度序（swizzle，见 03 篇）
```

静态并行（TP）：四个映射都是下标公式。动态并行（MoE）：前三个退化为运行时填充的查找表，顺序映射由排序结果决定。**先把四个映射写清楚，再谈 kernel 实现。**
