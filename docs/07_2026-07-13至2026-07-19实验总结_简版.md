# MoE 通信计算细粒度 Overlap 实验总结

## 1. 实现思路

目标是在四卡 PCIe TP MoE 中，将通信直接编排进 MoE kernel，以 token 和
GEMM tile 为粒度推进通信与计算，而不是把 GEMM 拆成 chunk 后放到不同 stream
中做粗粒度 overlap。

### L0：AllGather 与 W1 GEMM 重叠

L0 采用“源端 push、目标端本地 scatter、数据就绪后立即计算”的流水线：

```text
本地 FP8 token
  → push 到其他 rank 的 staging buffer
  → release flag 通知数据到达
  → 目标 rank 从本地 staging scatter 到 expert slot
  → 更新 row-block ready counter
  → 对应 GEMM tile 立即开始计算
```

具体实现如下：

- 每个 rank 将本地 token 和 scale 按目标 rank 的消费顺序直接 push 到对端
  staging buffer。每个 staging plane 只有一个源 rank 写入，避免多写者冲突。
- 数据写完后使用 system fence 和 release store 发布 per-token sequence flag；
  目标 rank 使用 acquire load 等待 flag，保证读到完整数据。
- 目标 rank 收到 token 后只访问本地 staging buffer，将数据 scatter 到该 token
  对应的 8 个 expert slot。
- 每完成一个 slot 的一段数据，就更新对应 row block 的 ready counter。
  GEMM block 不需要等待整个 AllGather 完成，只等待自己负责的 row block 就绪。
- 通信 block 完成 token 搬运后会转岗执行剩余 GEMM task，避免通信结束后 SM 空闲。

这样形成了：

```text
token push → token scatter → row block ready → GEMM tile
```

不同 token、不同 row block 和不同 GEMM tile 可以同时处于流水线的不同阶段，
实现细粒度通信计算重叠。

### L1：W2 GEMM、预归约与 ReduceScatter 重叠

L1 在 W2 GEMM 的输出阶段直接进行本地 top-k 预归约，并将归约后的结果推送到
目标 rank：

```text
W2 GEMM row block
  → 本地 top-k pre-reduce
  → push 到目标 rank
  → 发布 watermark/完成信号
  → 目标 rank 收到后立即进行最终归约
```

每个 row block 计算完成后即可进入预归约和通信，不需要等待全部 expert GEMM
结束。目标 rank 也可以按到达顺序消费远端结果，因此 W2 计算、本地归约、跨卡
传输和最终归约能够形成连续流水。

### Kernel 内的资源分工

融合 kernel 中的 SM 动态承担两类角色：

- 通信 SM：负责 token push/scatter、完成信号和 row-block counter；
- 计算 SM：从全局 task dispenser 领取已经满足依赖的 GEMM tile。

通信 SM 完成任务后通过 named barrier 汇合并转岗为计算 SM。L0、L1 各自在对应
阶段的 persistent kernel 内完成通信和计算编排，不需要为该阶段额外启动通信
kernel，也不依赖多 stream 的 chunk 切分。

## 2. 实验结果

实验使用四张 RTX PRO 5000，TP=4，FP8 输入和权重，每 rank 512 tokens。
vLLM serial baseline 将通信和计算 kernel 串行执行。

### 方案 A：将通信放进 GEMM producer warp

方案 A 尝试利用 GEMM producer warp 的空闲 lane 执行 peer pull，使 GEMM 使用
全部 SM。

| 实现 | T=512 | T=1024 | 结果 |
|---|---:|---:|---|
| 默认融合路径 | 1709µs | 2932µs | 对照 |
| L0+L1 通信 warp 化 | 1930µs | 3434µs | 分别慢 12.9%/17.1% |

探针实验发现，peer TMA read 与 GEMM 的本地 TMA tile load 共用同一 SM 的 TMA
队列，产生约 226µs 的 head-of-line blocking。结论是：在该平台上，将通信和
dense GEMM 塞进同一个 SM，比保留专职通信 SM 更慢，因此该方案关闭。

### P1：通信 block 内 per-lane 独立拉取

P1 保留专职通信 SM，但把原先一组 lane 同步等待最慢 PCIe 请求的方式，改为每个
lane 独立领取和处理 token。

| 实现 | T=512 | T=1024 |
|---|---:|---:|
| 波同步 pull | 1709µs | 2935µs |
| per-lane pull | **1681µs** | **2831µs** |

P1 在所有 `comm_sms` 档位都优于波同步版本，但最佳点仍需要 24 个通信 SM。
这说明 pull 的主要瓶颈是 PCIe 往返延迟和在飞请求数量，减少同步只能消除波内
长尾，不能减少隐藏 RTT 所需的并发度。

### P2：源端 push 与收端本地 scatter

P2 将通信方向从 peer pull 改为 posted write。源 rank 主动 push token，目标
rank 只需等待 flag，然后从本地 staging buffer scatter 数据。

| 实现 | T=512 | T=1024 |
|---|---:|---:|
| vLLM serial FP8 | 2074µs | 4030µs |
| per-lane pull | 1681µs | 2831µs |
| **push + local scatter** | **1629µs** | **2777µs** |
| 相对 serial 的耗时降低 | **21.5%** | **31.1%** |

push 路径使用 2 个 SM 就能达到饱和，说明 PCIe wire 已经退出关键路径。此时主要
瓶颈转移到收端本地 scatter：旧实现由单 lane 串行执行 8 次 TMA store 和一次
`store_async_wait`。

### P2.5：warp 协作 scatter

进一步的 P2.5 将 scatter 改为每个 warp 协作处理一个 token，32 个 lane 并行
搬运 staging 数据，使用普通向量 load/store，移除每 token 的 TMA、mbarrier 和
`store_async_wait`。

正确性和性能步骤有通过记录，但具体结果 JSON 没有保存，性能尚未完成正式定案，
因此当前默认仍使用 P2 的 push + lane scatter，最好结果为
**1629µs（T=512）和 2777µs（T=1024）**。

## 3. 结论

本轮实验表明，四卡 PCIe MoE 的有效细粒度 overlap 方式是：

1. 在一个 persistent kernel 内同时保留通信和计算角色；
2. 以 token、row block 和 GEMM tile 为流水粒度；
3. 源端使用 posted write 主动 push，避免目标端 peer-read RTT；
4. 用 release/acquire flag 和 row-block counter 建立数据依赖；
5. 数据块一旦到达就立即 scatter 和执行对应 GEMM tile；
6. 通信 SM 完成工作后转岗执行 GEMM，回收空闲算力。

最终实现相对 vLLM 串行 baseline 的耗时降低为：

- T=512：**21.5%**
- T=1024：**31.1%**
