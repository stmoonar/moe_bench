# 17 通信/计算重叠与融合算子性能损失分析(默认 shape E=64/hidden=4096)

**日期**:2026-07-09
**目的**:量化当前默认路径(pull dispatch⊕gate+up GEMM + prered combine)里
(a) 通算重叠了多少,(b) 融合算子比纯计算 GEMM 慢了多少。为 T6-v1(combine push 化)
提供 baseline 与目标。
**方法**:`tools/analyze_overlap.py`,4 卡(9,11,13,15)锁步,真实 dispatched 形状,
NE=64(默认 E=64,world=4 → E_local=16,每专家 ~256 token),取 max-over-ranks。
每层测「纯 GEMM(compute-only 参考)」vs「融合(comm+compute)」,差值 = 融合损失。

---

## 1. 结论速览

| 段 | 纯 GEMM | 融合 | 融合损失 | 效率 | 通信重叠 |
|---|---|---|---|---|---|
| **layer0** dispatch⊕gate+up | 900µs (229 TF) | 1176µs (175 TF) | **+276µs (+30%)** | 掉 24% | 部分(见 §2) |
| **layer1** prered combine | 508µs (203 TF) | 794µs (+56%) | **+283µs (+56%)** | 掉 36% | **≈0%** |

两层融合总损失 ≈ **560µs**,占 e2e 2330µs 的 **~24%**。**layer1 的通信几乎完全没被计算掩盖**
(重叠 ≈ 0),是 T6-v1 的直接目标。

## 2. Layer0:dispatch ⊕ gate+up GEMM

- 纯 gate+up GEMM(N=2·inter=6144,npl=4096):**900µs @ 229 TFLOP/s**;
- 融合(跨卡 pull token + 同 kernel gate+up GEMM):**1176µs @ 175 TFLOP/s**;
- **融合损失 +276µs(+30%)**。

含义:跨卡 pull 是与 GEMM 同 kernel 融合的(producer warp 自旋等 token,consumer 算
GEMM),理论上 pull 应藏在 GEMM 下。实测融合仍比纯 GEMM 慢 30%——说明 pull 只**部分**
被掩盖:16 个 comm SM 让渡 + producer 等待跨卡数据的气泡,使 GEMM 效率从 229 掉到 175。
但注意:纯 GEMM 900µs 已含 T4 的 gate+up 合并(N 翻倍),GEMM 本身是大头;pull 的
绝对代价(~276µs)相对可接受,且 dispatch 在此 shape 偏 compute-bound(docs/15 结论),
优化空间有限。

## 3. Layer1:prered combine(重点,T6-v1 目标)

- 纯 W2 GEMM(npl=4096,inter=3072,H=4096):**508µs @ 203 TFLOP/s**;
- 融合(W2⊕本地预归约 + barrier + 源卡 final_reduce):**794µs @ 130 TFLOP/s**;
- **融合损失 +283µs(+56%)**。

**损失分解**:

| 子段 | 时间 | 说明 |
|---|---|---|
| W2⊕prered(GEMM + 本地预归约,无 barrier/final) | 584µs | 比纯 GEMM +77µs = 预归约 job block 的散射+本地信号 |
| barrier + final_reduce | +207µs | 跨卡发布 barrier + 源卡拉各贡献卡 partial 行求和 |
| **合计融合损失** | **+283µs** | |

**通信重叠 ≈ 0% 的证据**:
- `final_reduce` 单独跑(源卡跨卡 gather partial 行,barrier 预满足)= **195µs**;
- 但 layer1 融合损失 = 287µs **>** 195µs;
- 若 final_reduce 的 195µs 通信被 W2 GEMM 掩盖,融合损失应 < 195µs。实测反而更大,
  说明 **final_reduce 完全串在 GEMM 之后**(t_fused ≈ t_GEMM + t_prered_scatter + t_barrier
  + t_finalreduce,零重叠),额外的 ~90µs 是 barrier + prered 散射 overhead。

**根因**(docs/12 的"零重叠"病在 prered 版依然存在):当前 prered 是三段串行——
(1) W2 GEMM 写完所有 expert_out → (2) job block 预归约写 partials → (3) 全卡 barrier →
(4) 源卡 final_reduce 拉。数据面(源卡 pull partial)必须等 barrier,barrier 必须等所有
卡的 prered 写完,prered 必须等 GEMM 写完。整条链没有边算边通的机会。

## 4. 对 T6-v1 的指导

T6-v1(数据面反转:expert 卡侧 partial 就绪即 TMA push 到源卡 staging + 水位信号)
要解决的正是 §3 的零重叠:
- **消 barrier 串行**:partial 行一旦算好立即 push(强路径 51GB/s),不等全卡 barrier;
- **边算边推**:GEMM 写完一个 row block → 该 block 的 prered 行就绪 → 立即推,推流贯穿
  整个 W2 GEMM,把 ~195µs 的跨卡传输藏进 508µs 的 GEMM 之下;
- **源卡终归约只等水位信号**:不再 per-token 等,HOL 消失。
- **目标**:layer1 融合损失从 +283µs 压到接近 prered 散射本身(~77µs)+ 少量尾巴,
  即 layer1 从 794µs → ~560~600µs,e2e 再省 ~200µs。

风险与验证同 docs/11 §3:dpush3 骨架镜像,内存序链 = push3 R1 同款,`validate_push3`
方法论直接搬;先做 push-only debug 入口对账 staging 内容,再全链路。
