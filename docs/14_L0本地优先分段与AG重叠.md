# L0 本地优先分段：让本地 token 的 W1 GEMM 不等 AllGather

> 分支 `ag_local_overlap`。开关 `TK_LOCAL_FIRST`（默认 0）。
> 立项动机、代价账、判决口径都在本文；结论回填 §6。

## 1. 问题

当前 L0 已经是"AllGather ⊕ W1 GEMM"融合（docs/02 §3、docs/07 §5），但**没有任何
GEMM 行块是可以零等待开算的**：

gathered 的行布局是全局 canonical 的 expert-major——expert `e` 内按
`(src_dev, src_tok, kpos)` 升序，所有 rank 逐字节相同。主配置
（E=64、T=512/rank、world=4、TopK=8、balanced）下每 expert 恰好 256 行，
每个 rank 贡献 64 行：

```
expert e 的 256 行:  [r0 的 64][r1 的 64] | [r2 的 64][r3 的 64]
                     └── 行块 2e ──────┘   └── 行块 2e+1 ─┘
```

`dispatch_gate_p` 的放行条件是**行块计数 == ROW_BLOCK(128)**，而每个行块都混了
两个 src_dev。于是对任意 rank，**它自己那 64 行虽然不用通信就在本地
（`scatter_lane` 的 `src == dev_idx` 分支直读 `pre_tokens`，连 staging 都不落），
却仍然要陪着另外 64 行等 peer 的到达 flag**。GEMM 的第一个 tile 必须等第一批
PCIe push 落地，本地数据的算力窗口白白让掉。

## 2. 方案：按"本地/远端"分段，本地段排在任务序最前

gathered 布局改为 **rank-dependent 两段式**（每个 rank 建自己的表；见 §3 论证
为什么数据面允许）：

```
行块 0 .. E-1        段 1（本地段）: 行块 e 只装 expert e 的**本 rank** assignment
行块 E ..            段 2（远端段）: 按 expert 升序装其余 rank 的 assignment
```

每段各自按 ROW_BLOCK 补齐。于是：

- **段 1 的每一行都来自 `pre_tokens`，scatter 不等任何 flag** → 行块计数在
  scatter 一开工就能满，`dispatch_gate_p` 立即放行；
- dispenser 的任务空间是扁平的 `task t -> row_idx = t / col_blocks`，行块按 id
  升序被 claim，所以 **前 `E × col_blocks` 个任务全部落在段 1**——GEMM 从第一个
  task 起就满负荷，整个 AllGather 窗口都有不依赖通信的活干；
- 段 2 的行块仍走原来的到达 gate，语义逐字不变。

关键前提（已逐条核实）：

1. `grouped_gemm_sm120_fp8_dispenser` 的行块→expert 映射**完全**由
   `blk_expert[row_idx]` 查表（sm120_common.cuh:440/494），没有任何地方要求同一
   expert 的行块连续；
2. `padded_tokens_per_expert` 的**值**从未被任何 kernel 读——L0/L1 entry 只用
   `padded.size(0)` 取 E，行块总数走 `num_padded_local_tokens / ROW_BLOCK`。
   所以 `padded[e]` 保持"expert e 的两段 padded 行数之和"即可，
   `bincount(blk_expert) == padded/ROW_BLOCK` 这条 preflight 不变量仍然成立。

## 3. 为什么 rank-dependent 布局是合法的（数据面不受影响）

历史注释写着"push 数据面要求所有 rank 认同同一套布局"，这句话对**当时**的
pull 数据面成立，对 P2 的 push 数据面已经不成立：

- **push 落点与布局无关**：`push_lane` 写的是 staging 的第 `d = src_dev*T + src_tok`
  行（tk_moe.cu:289-295），到达 flag 也按同一个 `d` 索引。源端从头到尾不需要知道
  目的卡的 gathered 布局。
- **scatter 用的是本地表**：`scatter_lane` 读**本地** `tp_slots[{d, k}]`
  （tk_moe.cu:344）决定散到哪几个 slot。每张卡用自己的布局即可。
- **`push_order` 仍然跨 rank 一致**（preflight 的 canonical 断言继续成立）。
  证明：`push_order[s]` 是源 s 的 token 按其 min slot 的排序。任一目的卡上，
  两段都按 expert 升序排布，故 min slot 的序 = `min_e(t)` 的序；`min_e` 相同时，
  段 1 内按 `src_tok` 排、段 2 内按 `(src_dev, src_tok)` 排——同源比较退化为按
  `src_tok`。两者给出同一个排列，与"在哪张卡上建表"无关。∎
- **`pull_order` 自动变成本地优先**，无需改公式：本地 token 的 8 个 slot 全在段 1
  （min slot < E×128），远端 token 全在段 2，按 min slot 升序排序天然把本地 512 个
  token 排到最前——scatter lane 一开工就先把段 1 喂满。

## 4. 代价账（必须先认清）

段 1/段 2 各自补齐会多出 padding。用 bench 的**真实路由生成器**（`data.py`
`_make_routing`）跑调度表实算（成本按两级 tile 口径：满块 1.0、64 行尾块 0.6，
docs/09 v3 实测）：

| 路由 | T | 布局 | 行块 | 尾块 | 成本 | Δ成本 | 行数 P | ΔP |
|---|---:|---|---:|---:|---:|---:|---:|---:|
| balanced | 512 | canonical | 128 | 0 | 128.0 | | 16384 | |
| | | **local_first** | 192 | 128 | 140.8 | **+10.0%** | 24576 | +50% |
| balanced | 1024 | canonical | 256 | 0 | 256.0 | | 32768 | |
| | | **local_first** | 256 | 0 | 256.0 | **+0.0%** | 32768 | **+0%** |
| uniform | 512 | canonical | 159 | 31 | 146.6 | | 20352 | |
| | | **local_first** | 192 | 65 | 166.0 | +13.2% | 24576 | +21% |
| uniform | 1024 | canonical | 288 | 32 | 275.2 | | 36864 | |
| | | **local_first** | 317 | 61 | 292.6 | +6.3% | 40576 | +10% |

- **balanced T=512 是最坏点**：每 expert 每 rank 恰好 64 行 = ROW_BLOCK 的一半，
  两段都只能各摊一个半空块。L0 GEMM ≈ 666µs → **+67µs**；L1 GEMM ≈ 349µs →
  **+35µs**；act 量化 ≈ 35µs（按 +50% 行数）→ **+17µs**。合计 **≈ +118µs**。
  收益上界 = 现状 L0 的 gate 等待（L0 exposure 93.9µs 的一部分，另一部分是 24 个
  comm SM 的让渡税，本方案回收不了），**所以预期为负，除非 gate 等待 > 118µs**。
- **balanced T=1024 是甜点，代价严格为零**：每 expert 每 rank 恰好 128 行 = 一个
  满块，段 2 = 384 行 = 3 个满块，行数、块数、尾块数与 canonical **完全相同**——
  机制收益全额落袋，没有任何税。**判决必须以这一档为主**，T=512 只是最坏点参照。
- 一般规律：代价 ≈ 每 expert 每 rank 的行数对 ROW_BLOCK 的对齐损失，`T*TopK/E/RB`
  越接近整数越便宜。主配置 E=64/TopK=8 下 T=1024 整除，T=512 恰好踩在半块上。

> 两级 tile（`TK_TWO_LEVEL`，默认开）是本方案的前置依赖：段 1 的 64 行块靠它把
> 成本压到 0.6。`TK_LOCAL_FIRST=1` 时若 `TK_TWO_LEVEL=0`，代价退化为 +50%，
> 只应在归因时使用。

### 4.1 二阶风险：L1 的跨卡 push 窗口被压缩（A/B 必须盯 `L1_fused`）

L1 的 job（本卡对某 token 的 TopK 预归约 + 回推源卡）在其 8 个 slot 的行块都算完
后才就绪，`job_order` 按 max slot 排 = 就绪序。canonical 布局下每个 token 的 8 个
slot 散布全局，**本地 job 与远端 job 的就绪时刻混合均匀**；local_first 下本 rank
自己的 token 全部落在段 1，于是：

```
canonical : [跨卡 push 均匀铺满整个 L1 GEMM ~384µs]
local_first: [段1 ~27%: 只有本地 job → 零跨卡流量][段2 ~73%: 全部跨卡 push]
```

本卡要回推的远端 job 是 `(world-1)*T = 1536` 行 × 8KB ≈ 12.6MB，按 posted write
50.9GB/s 需 ~247µs，而窗口从 ~384µs 收窄到 ~280µs——**余量从 1.55× 降到 1.13×，
L1 的 RS 有被暴露到尾部的风险**。

若实测 `L1_fused` 明显回退，Phase 2 的解法是给 dispenser 加一张可选的行块访问
顺序表 `row_perm`（`row_idx = row_perm[t / col_blocks]`），**L0 传 nullptr 保持段 1
优先，L1 传"段 2 优先"的排列**——L1 不需要本地优先（它的输入已经在本地），先算
远端行块就能把跨卡 push 提前铺开。本轮不做，保持单变量。

## 5. 探针：先量出 gate 等待的真实成本

新增 `TK_L0_NOGATE=1`（`entry_push` 的 `no_gate` 参数）：`dispatch_gate_p` 直接
返回，GEMM 不等行块计数。**结果数值是错的**（会读到未 scatter 的行），只用于计时：

```
gate 等待成本 = t(L0_fused) - t(L0_fused, NOGATE)
```

这是本方案收益的**硬上界**——本地优先最多也只能消掉段 1 那部分的等待。跑法见
§7 步 1；判据：若 gate 成本 < 40µs，则 balanced 档不必再做 A/B，直接看 T=1024。

## 7. 上机 runbook

先确认卡空闲。`TK_LOCAL_FIRST=1` 会关掉融合 sched kernel（回退 torch 版，
sched +~120µs），所以**裁决看 `time_tp_stages` 的分阶段数字，不看 e2e**；
e2e 只在机制判正后补融合版再报。

```bash
cd /workspace
rm -rf moe_bench/kernels/tk/build && python moe_bench/kernels/tk/build.py 4 2>&1 | grep -E 'registers|spill'

# 1) 回归门: 默认路径(local_first=0)必须零变化 —— rel_err 逐位 0.042817506939172745
CUDA_VISIBLE_DEVICES=0,1,2,3 python -m moe_bench.tools.run_tktp --iters 10

# 2) 探针: gate 等待成本上界(NOGATE 的输出数值是错的, 只读时间)
CUDA_VISIBLE_DEVICES=0,1,2,3 python -m moe_bench.tools.time_tp_stages 64 20 512
TK_L0_NOGATE=1 CUDA_VISIBLE_DEVICES=0,1,2,3 python -m moe_bench.tools.time_tp_stages 64 20 512
#    判据: 两者的 L0_fused 之差 < 40µs → balanced 档不必再 A/B(代价 ~118µs), 直接跳到步 4

# 3) 正确性门(单步隔离, 首次跑 local_first 布局): rel_err 必须与步 1 逐位一致
TK_LOCAL_FIRST=1 CUDA_VISIBLE_DEVICES=0,1,2,3 python -m moe_bench.tools.run_tktp --iters 10

# 4) A/B 分阶段(T=1024 = 零 padding 甜点, 主判决档; T=512 = 最坏点参照)
for T in 1024 512; do
  CUDA_VISIBLE_DEVICES=0,1,2,3 python -m moe_bench.tools.time_tp_stages 64 20 $T
  TK_LOCAL_FIRST=1 CUDA_VISIBLE_DEVICES=0,1,2,3 python -m moe_bench.tools.time_tp_stages 64 20 $T
done
#    读四个数: L0_fused(应降) / L0 exposure(应趋 0) / L1_fused(§4.1 风险) / P(行数)
```

## 8. 正确性判据（强）

布局重排**不改变任何一行的数值运算序**：

- 每个 gathered 行的 GEMM 是独立的 `A行 × B`，K 维累加序不变 → 逐位相同；
- L1 预归约按 `kpos` 顺序加权求和该 token 的 8 个 slot（顺序由 `tp_slots` 的列
  给定，与行的物理位置无关）→ 逐位相同；
- final reduce 按 src rank 顺序求和 → 不变。

所以 **`TK_LOCAL_FIRST=1` 与 `=0` 的端到端 rel_err 必须逐位一致**
（balanced 基线 `0.042817506939172745`）。不一致即为实现 bug，不是精度问题。

## 9. 死锁审计（AGENTS.md 红线）

**本方案不新增、不修改任何等待点。**逐条：

| 等待点 | 生产者 | 变化 |
|---|---|---|
| `dispatch_gate_p` 自旋（行块计数 == 128） | 本卡 scatter lane 的 `red.release.gpu.add` | 无。段 1 的计数由本卡 scatter 直接喂（连 peer 都不涉及），段 2 与现状同源同语义；仍有 `PCIE_SPIN_GUARD` 有界 trap |
| `scatter_lane` 等到达 flag | peer 的 `st.release.sys` | 无。段 1 的行走 `src == dev_idx` 分支**根本不进自旋**；段 2 与现状逐字相同；仍有 5e8 次自旋上界 trap |
| `push_lane` 的 `guarded_wait` | 本卡 TMA | 无 |
| `pcie_barrier_all` | 各 rank release store | 无 |
| GEMM 流水 mbarrier | 同 kernel 内 producer | 无 |

跨 rank 依赖链仍为 `GEMM ← scatter ← flag ← peer push`，无环。`TK_L0_NOGATE`
探针只**移除**一个等待点，不新增。行块计数的初值仍由 `reset_kernel_p` 按 slack
重置，slack 表与布局同源重建（host golden 逐元素对拍）。
