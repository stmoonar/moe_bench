# 38 FP8 P1:正确性一次达标、性能 1.29×、fp32 累加税假说与裁决探针

> 两轮实测(112308 首测 / 113831 预取版)。承接 docs/37。

## 1. 已定的结论

- **正确性一次全对**:L0(K=4096,N=1536)与 L1(K=768,N=4096)两档
  rel_err = 1.68e-3(< 5e-3 阈)——per-row scale 映射(rt 行布局
  data[偶]→lane/4、data[奇]→+8)、B^T + mma_ABt、per-128K fp32 重标定
  全部正确;
- **TK 平台坑(沉淀)**:col-layout 的 fp8 寄存器加载在 TK 里没写完
  (`shared_to_register.cuh` 对 fp8x4 用 .x/.y,编译不过);解法 = B 全面
  转置布局 (E,N,K) + row-layout ldmatrix + `mma_ABt`(fp8 特化 SM120
  齐全)。副产品:(E,N,K) 是 w1 原始布局,P2 集成免转置;
- **scale 预取假说证伪**:边界 scale 读延迟只值 +1.5%(1.27→1.29×),
  不是主瓶颈(预取代码保留,无害)。

## 2. 性能现状与 fp32 累加税假说

fp8 283 TFLOP/s / bf16 220 = **1.29×**(L1 形状 1.34×),距 2× 相去甚远,
但一个硬件假说把数字解释得近乎严丝合缝:

**GeForce/工作站硅的 fp32 累加税**:自 sm_89 起,
`mma.*.f32.e4m3.e4m3.f32` 的指令率是 f16 累加版的一半——每指令 2× MAC ×
1/2 率 = **fp8+fp32acc 的 FLOP/s 峰值 ≈ bf16 峰值**。按 110 SM × ~2.57GHz
估算 bf16 峰值 ≈ 289 TFLOP/s:我们的 fp8 = 283 = **98% 税后天花板**,
bf16 kernel = 220 = 76%。fp8 的 +29% 全部来自字节减半(A/B tile 各半,
smem/HBM 压力减半,mma 管线更易喂满),不是 mma 变快。

f16 累加能免税拿 2×,但 DeepSeek 式 128-K 块内 f16 累加有真实溢出风险
(量化值 RMS ~128,128 个积的随机游走 RMS ≈ 92k > fp16 max 65504)——
这正是 DeepSeek 在 Hopper 用 fp32 promotion 的原因,GeForce 系没有免费
出路。若税坐实,这是 sm120 移植的一手平台事实:
**blockwise fp8 在消费级硅上的收益上限 ≈ 1.3×(来自带宽),不是 2×**。

## 3. 裁决探针(已落码)

`grouped_gemm_fp8(..., raw=True)`:RESCALE=false 模板实例,跳过全部重标定
FFMA 与 scale 读(结果错,只测纯 mma+流水吞吐)。工具输出 `raw-cap`:

- **raw ≈ 290 附近 → 税坐实**:接受 fp32acc 版(正确、已贴天花板),
  P2/P3 按修订账推进:L0 GEMM 969→~750、L1 508→~380,
  e2e ~1770 vs serial fp8 2074 ≈ **1.17×**(+bf16 阶段遗留的 sched/L0
  优化空间 → ~1.2×;T=1024 优势更大);
- **raw 显著 >290(如 >350)→ 瓶颈在结构**:回头查 FFMA 占比/流水深度
  (PIPELINE_STAGES 3→5,smem 有 30KB 余量)/b_reg 加载路径。
