# 21 经验：torch 默认设备坑 + 远程 zip 回流的调试工程实践

> TP 分支（tp_test）前两轮上机迭代沉淀的**经验**（结果与归因见 docs/20）。
> 三部分：① 一个必踩的 torch 坑；② 无 GPU 本地开发 + 远程 zip 回流的工作流
> 工程实践；③ 无 profiler 情况下的归因方法论。

## 1. 坑：`torch.set_default_device(cuda)` 吃掉 host 侧调度表

**现象**（首轮上机，tp_run_20260711_123548）：所有 tktp 步骤在 setup 就挂，
`torch.cat` 报 "Expected all tensors to be on the same device... cpu, different
from other tensors on cuda:N"。

**根因**：`distributed.py` 的 worker 统一执行 `torch.set_default_device(device)`。
此后**任何不带显式 `device=` 的张量创建都落在 GPU 上**。host 侧调度构建
（python 循环填表）里 `torch.zeros(1)`、`torch.full(...)` 这类"显然是 CPU 临时表"
的创建全部被劫持：轻则 cpu/cuda 混用直接报错，重则**python 循环逐元素赋值变成
16k+ 次单元素 GPU 写**（不报错但慢到离谱，更隐蔽）。

**为什么本地测试没拦住**：本地无 GPU，默认设备就是 cpu，测试全绿。
默认设备是**环境状态**，纯逻辑测试测不出环境敏感性。

**纪律**（EP 的 `_build_schedules` 早已遵守，TP 版漏抄）：

- host 侧表构建函数里，**每一个**张量创建都写显式 `device="cpu"`；
  GPU builder 里每一个都写 `device=device`。没有例外，包括
  `torch.zeros(1)` 这种一次性小张量。
- 自查方法：`grep -nE 'torch\.(zeros|full|empty|ones|arange|tensor)\(' <file>`，
  逐行确认都有 device 参数。
- 衍生规则：任何"在 worker 环境里跑"的代码，不能假设默认设备/默认 dtype/
  默认 stream 是干净的。

**元教训（第三轮再踩同一个坑）**：写下上述纪律的**同一轮**，新增的
pull_order/job_order 代码里 `torch.arange(S)` 又漏了 device——grep 审计是在
加新代码**之前**做的，"改完再 grep"靠自觉不成立。第三轮上机因此整轮报废
（tp_run_20260711_131801，全部 tktp 步骤死在同一行）。

**根治**：`tools/preflight_tp_cpu.py`——用 `TorchFunctionMode` 拦截构建器内
所有不带显式 device 的张量创建（机器强制，非人肉 grep），连同表裁决 +
数据流模拟一起做成 CPU 预检（无 GPU/vllm 依赖，本地随手跑；一键脚本
step 00 在编译/烧卡之前先跑，失败直接打包退出）。**纪律要活下来，
必须变成机器检查**。

## 2. 远程 zip 回流工作流的工程实践

约束：本地无 GPU，目标机器不可直连——用户手动把一键脚本产物 zip 拿回来。
**每一轮回流的成本很高，脚本设计目标 = 单轮回流的信息量最大化**：

1. **单步 `timeout` + 失败不中断**：kernel 协议 bug 常表现为自旋死锁；
   没有 timeout 一步挂死全场空手而归。每步独立限时、失败记录后继续，
   坏一步仍能带回其余全部信息。
2. **失败要能远程归因**：静默吞异常是大忌。首轮就靠 summary 里的完整
   traceback 一眼定位（scheme 注册的 try/except 也改成了打印 traceback——
   否则远端只会看到 "Unknown scheme 'tktp'" 无从查起）。
3. **干净编译**：build 缓存按文件名（world/hidden/rb）判存在，改了 .cu
   不重编——脚本开头 `rm -rf kernels/tk/build`，防 stale .so 跑出"幽灵结果"。
4. **产物自带环境**：hostname/git rev/nvidia-smi/topo/版本全部进 zip，
   数字才可解释（比如挑了哪个卡组、是否同 PCIe switch）。
5. **顺手带上 sweep**：首轮的 comm_sms sweep 本是顺手加的，结果成了归因
   的决定性证据（§3）。回流成本高时，多带一组正交扫参很划算。
6. **前置环境检查要真实**：路径检查（TK submodule 在 moe_bench 内而非同级）
   首轮就写错方向白跑一次——检查逻辑要和真正的消费方（build.py 的相对路径）
   对齐，而不是凭记忆写。
7. **行尾是跨平台工作流的一部分**：Windows 上任何文本模式写文件（python
   `open(p, "w")`、部分编辑器）默认产出 CRLF，bash 直接报
   `$'': command not found` / `set: pipefail invalid`（第五轮开跑即挂）。
   根治 = 仓库 `.gitattributes` 强制 `*.sh/*.py/*.cu text eol=lf`（机器检查，
   同 §1 元教训）；脚本写文件一律 `open(p, "w", newline="
")` 或二进制写。
8. **本地能验的先验完**：调度表 host/GPU 双实现逐元素裁决 + CPU 数据流模拟
   （stub torch.distributed）两道锚点，把"逻辑错"和"环境/协议错"分离——
   上机后出的问题可以直接排除表逻辑，缩小归因范围。

## 3. 方法论：没有 profiler，账也能归因

首轮 tktp 慢 38%，没跑 ncu，三条账直接定位（细节 docs/20 §2）：

1. **资源 sweep 的形状**：comm_sms 4→24 e2e 改善 1950µs 且未收敛，
   同时"从 GEMM 抢 SM 反而变快" → 排除带宽 bound 与 GEMM bound，
   指向 comm block 排队串行。**sweep 曲线的方向和收敛性本身就是归因证据**。
2. **波数账**：疑似瓶颈（block 排空）可以闭式算：块数/并发 SM = 波数，
   波差 × 每块开销 ≈ 观测差值（426 波 ≈ 1700µs，对上）。对不上就换假设。
3. **量纲随规模的斜率**：绝对差随 T 线性（~0.45µs/job）→ 与"per-job 串行
   成本"一致，排除固定开销类解释。

配套纪律：把下一轮要对的账**先写进文档**（docs/20 §4 的预期账），回流后
逐项对数——预期差多少、实际差多少，偏差本身就是新的归因线索。

## 4. 可泛化的调度教训（对 EP/COMET 复刻同样适用）

- **依赖粒度的方向 > 一切微调**（experience 十条第 1 条的实证）：L0 ring
  拉取序让所有 row block 等最后一个 ring 段——"本卡优先"直觉在"消费块混源"
  的布局下完全失效。正确做法是让**到达序对齐消费序**（pull_order 按 min-slot
  排 = expert 主序），而不是对齐"源的远近"。
- **block-per-job 是反模式**：大 smem 配置下每 SM 驻一块，job 块排空以块
  调度为粒度串行。换**常驻块 + 原子 dispenser + 就绪序（job_order）**：
  块 churn 归零、流式消费保留、"全员收尾"（GEMM 完成的 comp 块加入排空）
  把尾部从 num_comm_sms 提速到全 SM。dispenser 保证每 job 恰好领一次，
  不动单写者/选举协议。
- **通信占比先算账再立项**（experience/01 §10 的实证）：TP serial 通信占比
  仅 ~23%（EP 40%+），完美重叠上限 ≈2.2ms vs serial 2.6ms——TP 融合的
  天花板结构性有限。相对机会在大 NE（serial 的 triton 实现随 NE 恶化）。
