**日期**：2026-07-08
**硬件**：16× RTX PRO 5000 72GB Blackwell（SM120），PCIe 互连
**测试卡组**：`CUDA_VISIBLE_DEVICES=9,11,13,15`（NUMA node1，两两 PIX 同 switch，优先级最高的四卡组合）

- SM 12.0，**110 SM**，71.1 GB 显存，**smem/block optin = 99 KB**，regs/SM = 65536。
- 与 experience/12 篇的画像一致（110 SM / 99KB smem），kernel 的 tile/stage 预算按此设计成立。

## 两个关键发现

### 1. 远端原子实际可用（与 12 篇「红线 2」相反）

本机 `cudaDevP2PAttrNativeAtomicSupported=1`，且三种远端原子（device-scope atomicAdd、
system-scope atomicAdd_system、`red.release.sys.add`）对 peer 显存实测全部返回精确值。

**影响**：这是「额外福利」而非必需。我们的融合方案本就走 **pull + 本地原子**（layer0 dispatch
把 token 拉到本地后本地 `red.release.gpu` 计数），无论远端原子是否可用都正确。因此：
- 现有 kernel 不用改，保持保守的 pull 路线。
- 但**未来 layer1 combine** 如果需要「推 + 目标卡归约」，本机可以直接用远端 `store_add`，
  不必强制走 12 篇的 slot 化协议——多一条可选路径。
- 谨慎：`nativeAtomics=1` 通常暗示拓扑其实不是纯 PCIe（可能有更强的互连或 ACS 全放开）。
  不影响正确性，但性能账要以实测为准。

### 2. SM 驱动 pull 带宽偏弱且不对称（风险点）

- **push**（本地读、写 peer）：所有卡 4~8 block 就饱和到 ~51 GB/s，接近 CE。
- **pull**（读 peer、写本地）：dev0 能爬到 51 GB/s（需 16 block），但 **dev1 封顶 ~20 GB/s**。

**影响**：layer0 dispatch 用的正是 **TMA pull**（从 peer 卡拉 token 向量）。这直接命中 PLAN 的
风险 R2/R3——逐 token pull 可能打不满带宽。Phase 2 要：
1. 用 nsys 确认 dispatch 是否拖尾；
2. 加大 pull 流水深度（每 block 多 outstanding TMA）；
3. 若 pull 塌陷，回退到「源端 pack + push」或「CE 大块搬运」（R2 回退）。
4. dispatch 的 comm SM 数（`num_comm_sms`）sweep 要往大了给一点（8~16），因为单 block pull 很慢。

## 结论

**全盘 GO**。P2P 通、带宽足、信号可见性正常。唯一要盯的是 SM pull 带宽不对称——这是 comm 侧
的性能风险，不是正确性风险。可以进入 Phase 1。
