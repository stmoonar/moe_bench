# L0 本地优先分段：让本地 token 的 W1 GEMM 不等 AllGather

> 分支 `ag_local_overlap`。开关 `TK_LOCAL_FIRST`（默认 0）。
> 立项动机、代价账、判决口径都在本文；结论回填 §6。

## 1. 问题

当前 L0 已经是"AllGather ⊕ W1 GEMM"融合（docs/02 §3、docs/07 §5），但**几乎没有
GEMM 行块是可以零等待开算的**：

gathered 的行布局是全局 canonical 的 expert-major——expert `e` 内按
`(src_dev, src_tok, kpos)` 升序，所有 rank 逐字节相同。以完美对齐的 balanced
（E=64、T=512/rank、world=4、TopK=8）为例，每 expert 恰好 256 行，每个 rank
贡献 64 行：

```
expert e 的 256 行:  [r0 的 64][r1 的 64] | [r2 的 64][r3 的 64]
                     └── 行块 2e ──────┘   └── 行块 2e+1 ─┘
```

`dispatch_gate_p` 的放行条件是**行块计数 == ROW_BLOCK(128)**，而每个行块都混了
两个 src_dev。于是对任意 rank，**它自己那 64 行虽然不用通信就在本地
（`scatter_lane` 的 `src == dev_idx` 分支直读 `pre_tokens`，连 staging 都不落），
却仍然要陪着另外 64 行等 peer 的到达 flag**。GEMM 的第一个 tile 必须等第一批
PCIe push 落地，本地数据的算力窗口白白让掉。

不均匀路由（uniform/skewed，真实业务形态）下会偶然出现少量纯本地领头块
（实测 0~2.2% 的工作量，见 §4 的 canon 行），但那是运气，不是机制。

## 2. 方案：按"本地/远端"分段，本地段排在任务序最前

gathered 布局改为 **rank-dependent 两段式**（每个 rank 建自己的表；见 §3 论证
为什么数据面允许）：

```
行块 0 .. nb_local-1   段 1（本地段）: 只装**分了段的** expert 的本 rank assignment
行块 nb_local ..       段 2         : 其余一切（peer 的行 + 未分段 expert 的全部行）
```

每段各自按 ROW_BLOCK 补齐。**哪些 expert 分段是逐 expert 决定的**——见 §4，
不均匀路由下这是方案能不能免费的关键。于是：

- **段 1 的每一行都来自 `pre_tokens`，scatter 不等任何 flag** → 行块计数在
  scatter 一开工就能满，`dispatch_gate_p` 立即放行；
- dispenser 的任务空间是扁平的 `task t -> row_idx = t / col_blocks`，行块按 id
  升序被 claim，所以 **前 `nb_local × col_blocks` 个任务全部落在段 1**——GEMM
  从第一个 task 起就满负荷，这段时间完全不依赖 AllGather；
- 段 2 的行块仍走原来的到达 gate，语义逐字不变。

关键前提（已逐条核实）：

1. `grouped_gemm_sm120_fp8_dispenser` 的行块→expert 映射**完全**由
   `blk_expert[row_idx]` 查表（sm120_common.cuh:440/494），没有任何地方要求同一
   expert 的行块连续；
2. `padded_tokens_per_expert` 的**值**从未被任何 kernel 读——L0/L1 entry 只用
   `padded.size(0)` 取 E，行块总数走 `num_padded_local_tokens / ROW_BLOCK`。
   所以 `padded[e]` 保持"expert e 的两段 padded 行数之和"即可，
   `bincount(blk_expert) == padded/ROW_BLOCK` 这条 preflight 不变量仍然成立。

## 3. 为什么 rank-dependent 布局是合法的（数据面不受影响）

历史注释写着"push 数据面要求所有 rank 认同同一套布局"，这句话对**当时**的
pull 数据面成立，对 P2 的 push 数据面已经不成立：

- **push 落点与布局无关**：`push_lane` 写的是 staging 的第 `d = src_dev*T + src_tok`
  行（tk_moe.cu:289-295），到达 flag 也按同一个 `d` 索引。源端从头到尾不需要知道
  目的卡的 gathered 布局。
- **scatter 用的是本地表**：`scatter_lane` 读**本地** `tp_slots[{d, k}]`
  （tk_moe.cu:344）决定散到哪几个 slot。每张卡用自己的布局即可。
- **`push_order` 的排序键换成 `(min expert, src_tok)`**，于是跨 rank 一致
  （preflight 的 canonical 断言继续成立）。原来的键是"本地表的 min slot"，在
  **选择性**分段下会失效：本卡自己的 token 可能落进段 1（行块排在最前），本地
  min slot 的序就不再等于目的卡看到的消费序了。新键与建表的卡无关，因为两段都
  按 expert 升序排布，同源 token 的比较退化为按 `src_tok`。canonical 布局下新
  旧两个键**逐位等价**（段内 expert 升序、行内均无并列、都是全序且同序），
  preflight 有专门的等价断言，融合 sched kernel 的派生逻辑因此也不受影响。
  正确性其实不依赖这条性质——push 落点和到达 flag 都由 `src_dev*T+src_tok` 定死
  ——但"源按目的卡消费序推"是流水启发式，丢了会掉性能。
- **`pull_order` 自动变成本地优先**，无需改公式：分了段的 expert 的本地
  assignment 全在段 1（slot 最小），按 min slot 升序排序天然把它们排到最前——
  scatter lane 一开工就先把段 1 喂满。

## 4. 逐 expert 分段决策：让不均匀路由下的代价归零

段 1/段 2 各自补齐会多出 padding，但**这笔代价逐 expert 差别极大**，而且恰好
在不均匀路由下有一大批 expert 是免费的。给 expert e 单开本地段的边际成本是

```
d(e) = cost(c_local) + cost(c_remote) − cost(c_local + c_remote)
cost(n) = ⌈n/RB⌉ 个块，其中末块真实行 ≤ RB/2 时算 0.6（两级 tile），否则 1.0
```

- `c_all=260` 一段要 `2.6`；拆成 `c_loc=128 | c_rem=132` 是 `1.0 + 1.6 = 2.6`
  → **d = 0，白拿一个零等待块**；
- balanced T=512 的 `c_all=256 → c_loc=64 | c_rem=192` 是 `2.0 → 0.6+1.6=2.2`
  → d = +0.2，要付钱。

**均匀路由下所有 expert 的 d 相同（要么全免费、要么全收费），不均匀路由下 d 沿
expert 散开——于是"只分免费的那批"成为可能。** 这就是 `_local_seg_mask` 做的事：
阈值 `TK_LOCAL_SEG_THR5`（单位 1/5 满块当量，默认 **0** = 严格帕累托）。成本用
**整数**口径（满块 5、尾块 3）算，因为这个比较进的是调度表，host/GPU 两条构建
路径必须逐位同号。

用 bench 的**真实路由生成器**（`data.py` `_make_routing`）驱动真实调度表实算
（`head-blk` = 领头的、一条远端行都不含的行块数；占比 = 这些块占总块成本的比例，
即"零等待工作量"）：

读数：

- **thr5=0 在四个不均匀档全部是零代价，同时拿到 7.5%~16.6% 的零等待工作量**
  （canonical 的 0~2.2% 是偶然出现的纯本地领头块，是基线不是收益）。这是严格的
  帕累托改进——即使 gate 等待很小，也**不可能亏**。
- thr5 是一条清晰的收益-代价曲线，可以用它买更多零等待工作量：`skewed T=1024`
  花 +0.8% 从 16.6% 买到 19.2%，`uniform T=512` 花 +2.3% 从 7.5% 买到 14.1%。
  A/B 值得扫 `0/1/2`。
- `thr5=99`（全分段）就是原来的朴素方案，uniform/skewed 下要付 +5.8%~+15.7%，
  **不应作为默认**。
- `balanced T=512` 下 thr5=0 会退化成 canonical（所有 expert 的 d 都是 +0.2），
  表和布局与关闭开关时逐字相同——无收益也无代价，符合预期。

> 两级 tile（`TK_TWO_LEVEL`，默认开）是本方案的成本模型前提：`_blk_cost5` 里
> 64 行尾块记 0.6 就是它。`TK_LOCAL_FIRST=1` 时若 `TK_TWO_LEVEL=0`，实际代价会
> 高于决策所依据的模型，只应在归因时这样组合。

> **口径**：主判决档是 **uniform / skewed**（真实业务路由，docs/09 §1）。
> balanced 是完美对齐的上界口径——它的 `c_local` 恰好等于 `T·TopK/E/world`，
> 对 ROW_BLOCK 要么整除（T=1024）要么正踩半块（T=512），两种极端都不代表真实
> 负载下 `d(e)` 沿 expert 散开的形态，而后者正是本方案零代价的来源。

### 4.1 二阶风险：L1 的跨卡 push 窗口被压缩（A/B 必须盯 `L1_fused`）

L1 的 job（本卡对某 token 的 TopK 预归约 + 回推源卡）在其 8 个 slot 的行块都算完
后才就绪，`job_order` 按 max slot 排 = 就绪序。canonical 布局下每个 token 的 8 个
slot 散布全局，**本地 job 与远端 job 的就绪时刻混合均匀**；local_first 下本 rank
自己的 token 全部落在段 1，于是：

```
canonical  : [跨卡 push 均匀铺满整个 L1 GEMM]
local_first: [段1: 只有本地 job → 零跨卡流量][段2: 全部跨卡 push]
```

本卡要回推的远端 job 是 `(world-1)*T` 行 × 8KB（T=512 → 12.6MB ≈ 247µs @
50.9GB/s；T=1024 → 25MB ≈ 490µs），窗口按段 2 占比缩水：

| 档 | 段 1 占比 | L1 GEMM | 可用窗口 | 余量 |
|---|---:|---:|---:|---:|
| canonical | 0% | ~400µs (T=512) | 400µs | 1.6× |
| **thr5=0** | 7.5%~16.6% | 同上（零代价） | 334~370µs | **1.35~1.5×** |
| thr5=99（全分段） | ~28~32% | +6~16% | ~280µs | 1.13× |

**thr5=0 把这个风险也一并压小了**（余量 1.35× 以上），但仍需在 A/B 里盯
`L1_fused`。若实测明显回退，Phase 2 的解法是给 dispenser 加一张可选的行块访问
顺序表 `row_perm`（`row_idx = row_perm[t / col_blocks]`），**L0 传 nullptr 保持段 1
优先，L1 传"段 2 优先"的排列**——L1 不需要本地优先（它的输入已经在本地），先算
远端行块就能把跨卡 push 提前铺开。本轮不做，保持单变量。

## 5. 探针：先量出 gate 等待的真实成本

新增 `TK_L0_NOGATE=1`（`entry_push` 的 `no_gate` 参数）：`dispatch_gate_p` 直接
返回，GEMM 不等行块计数。**结果数值是错的**（会读到未 scatter 的行），只用于计时：

```
gate 等待成本 = t(L0_fused) - t(L0_fused, NOGATE)
```

这是本方案收益的**硬上界**——本地优先最多也只能消掉段 1 那部分的等待。跑法见
§7 步 2。

注意 thr5=0 档的代价实测为零（§4），所以**探针不再是"要不要做"的关卡，而是
"能拿回多少"的标尺**：gate 成本给出收益天花板，`零等待占比`（7.5%~16.6%）给出
实际能覆盖的比例。若 gate 成本本身就接近 0，说明 min-slot 的 pull 序已经把等待
消化掉了，本方案在当前 comm 配置下无收益（但也不亏）——那就该把 `TK_COMM_SMS`
往下扫，看通信 SM 减少、gate 等待抬头之后本方案能不能兑现。

## 8. 正确性判据（强）

布局重排**不改变任何一行的数值运算序**：

- 每个 gathered 行的 GEMM 是独立的 `A行 × B`，K 维累加序不变 → 逐位相同；
- L1 预归约按 `kpos` 顺序加权求和该 token 的 8 个 slot（顺序由 `tp_slots` 的列
  给定，与行的物理位置无关）→ 逐位相同；
- final reduce 按 src rank 顺序求和 → 不变。

所以 **`TK_LOCAL_FIRST=1` 与 `=0` 的端到端 rel_err 必须逐位一致**
（balanced 基线 `0.042817506939172745`）。不一致即为实现 bug，不是精度问题。

## 9. 死锁审计（AGENTS.md 红线）

**本方案不新增、不修改任何等待点。**逐条：

| 等待点 | 生产者 | 变化 |
|---|---|---|
| `dispatch_gate_p` 自旋（行块计数 == 128） | 本卡 scatter lane 的 `red.release.gpu.add` | 无。段 1 的计数由本卡 scatter 直接喂（连 peer 都不涉及），段 2 与现状同源同语义；仍有 `PCIE_SPIN_GUARD` 有界 trap |
| `scatter_lane` 等到达 flag | peer 的 `st.release.sys` | 无。段 1 的行走 `src == dev_idx` 分支**根本不进自旋**；段 2 与现状逐字相同；仍有 5e8 次自旋上界 trap |
| `push_lane` 的 `guarded_wait` | 本卡 TMA | 无 |
| `pcie_barrier_all` | 各 rank release store | 无 |
| GEMM 流水 mbarrier | 同 kernel 内 producer | 无 |

跨 rank 依赖链仍为 `GEMM ← scatter ← flag ← peer push`，无环。`TK_L0_NOGATE`
探针只**移除**一个等待点，不新增。行块计数的初值仍由 `reset_kernel_p` 按 slack
重置，slack 表与布局同源重建（host golden 逐元素对拍）。
