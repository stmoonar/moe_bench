# 07 评审：实现漏洞、对比公平性、下一步优化方向

**日期**：2026-07-08
**评审对象**：`tk_scheme.py` + `kernels/tk/{tk_moe.cu, sm120_common.cuh}` + benchmark harness（bench/distributed/schemes/data/reference）+ docs 01~06 的结果。

## 0. 先回答精度问题：不是在跟 fp8 比

Phase 4 的对比命令是 `--mode ep --precision bf16`。`data.py` 里 `precision=bf16` 时
`quant_config=None`，serial baseline 的 `fused_experts` 走的是 **bf16** 路径——所以当前是
**bf16 计算+bf16 通信 vs bf16 计算+bf16 通信，精度口径公平**。`deepseek_v32.yaml` 的默认
precision 也是 bf16。

两点提醒：
1. harness 支持 `--precision fp8`（serial 的 GEMM 变 fp8 block-quant，但它的 NCCL AG/RS
   **通信仍是 bf16** hidden_states）。DeepSeek 生产部署是 fp8，所以**最终要赢的对手是
   serial-fp8**——届时 tkfused 也上 fp8（传输+mma），对比仍是同精度 apples-to-apples，
   且 fp8 serial 的通信不会变快（还是 bf16 AG/RS），我们的 fp8 dispatch/combine 反而在
   通信上单方面受益。
2. 跑 serial-fp8 一次拿到数字，作为"最终目标线"记下来，避免 bf16 打平后误判收益空间。

## 1. 实现审查：发现的问题（按重要性排序）

### P1（公平性，对 TK 有利）：schedule 预计算不计时，serial 的等价工作在计时内

`_build_schedules` 的 host 四重循环在 `setup()`（不计时），而 serial 的 `fused_experts`
**每次 run 都在 GPU 上做** routing metadata（`moe_align_block_size` 排序/对齐）。真实
serving 中 routing 每个 batch 都变，schedule 是必须付的成本。当前 host 三重循环若计入会是
ms~十 ms 级，直接反超收益。
**处置**：(a) 短期在报告里注明口径差异；(b) 中期 schedule 上 GPU（`argsort`+`cumsum`
向量化，目标 <100µs）并**计入 run()**，这也是 Phase 4 文档已列的第 3 项。在此之前，
"打平 serial"的结论要打折扣。

### P2（健壮性）：pre_tokens 覆盖安全依赖一条隐式链，建议显式化

`run()` 里 `pre_tokens.copy_` 在 device_barrier **之前**。迭代 n+1 的 copy 会不会覆盖
peer 还在拉的迭代 n 数据？推演结论：**当前恰好安全**，链条是——
"e 卡拉 A 的 token ⇔ A 的 combine 等 e 的 W2 信号 ⇔ e 的 W2 kernel 已启动 ⇒（e 卡
stream 顺序）e 的 dispatch 已完成"，而 A 的 copy(n+1) 在 A 的 combine(n) 之后。
但这个安全性依赖"combine 等待集 = dispatch 拉取集"的对偶性和 stream 顺序，任何一处改动
（如跳过 combine、改等待粒度、单测只循环 layer0 且输入每轮变化）都会悄悄破坏它。
**处置**：在 copy_ 之前再加一次 `device_barrier`（+seq），成本 ~10µs 对 7ms 无感；或至少
把这条链写进 tk_scheme.py 注释。

### P3（性能账）：dispatch 逐 assignment 拉取，无 (token, rank) 去重

一个 token 路由到同一 expert 卡的多个 expert 时被拉多次。E=256/top8/4 卡 balanced 下，
每卡 assignments≈4096 而 unique 源 token≈1800——**去重可省 ~2.2× dispatch 流量**。
去重后需要 expert 卡本地 scatter 复制到各 slot（本地带宽百 GB/s 级，近乎免费）。

### P4（benchmark 覆盖）：单点 512 token、balanced-only、tk yaml `verify: false`

- 512 token/rank 下 per-expert 均值 64、padding 到 128 → **GEMM 算了 ~2× 的行**（这是
  对 TK **不利**的开销，说明 kernel 侧其实比表面数字强）。要么补 2048/8192 token 点
  （padding 占比降）看趋势，要么上 ROW_BLOCK=64 减 padding（见 §3）。
- `skewed`/`single` 分布没测——EP 的负载不均是生产常态，也是自旋等待协议最容易出尾延迟的地方。
- 性能跑用 `--no-verify` 可以，但至少保一条 256 专家的抽查路径（golden 显存问题可以用
  "只校验若干 token 行"的抽样 golden 解决，不必全量权重 upcast）。

### P5（小项）
- `run()` 里 `F.silu(gate)*up` 每次分配两个临时张量（违反 allocation-stable 契约的字面
  要求；caching allocator 下无碍但有 launch/allocator 开销）——可写 in-place 或小融合 kernel，
  顺手把它融进 layer1 的 A-tile 装载更好。
- `_time_scheme` 迭代间无 dist.barrier，靠 max-across-ranks 兜底——可接受，严谨起见可加。
- `disp::entry` 丢了 tileoverlap/02 里 "weights.size(0)==num_local_experts" 的 TORCH_CHECK
  （docs/03 记载的 NUM_GPUS 换挡坑正是靠这个 check 暴露的，建议补回）。
- `combine_signal_epilogue` 每 tile 全体线程 `__threadfence_system()`，fence.sc.sys 不便宜；
  正确性必需，但可测一下占比（ncu），若显著可改为"每 row block 最后一个 tile 才 fence+信号"
  需要重新推内存序，暂不动。
- combine block 按源 token 顺序排队，信号按 expert 行序到达 → 潜在 head-of-line 阻塞
  （早排队的 token 等晚就绪的 expert，占着 SM）。512 token/16 SM 排 32 轮，尾部可见。
  改 persistent combine worker + 就绪队列可解，优先级低于 §3 的大项。
- docs/02、04 引用的 `docs/05_关键bug_group_store行映射.md` 不在 docs 目录里（可能没从
  服务器同步），补上——那是最有含金量的一篇踩坑记录。

### 审查过、确认没问题的点
- combine 的内存序链（每 block fence.sys → acq_rel.gpu 计数 → 满额者 release.sys 广播 →
  源卡 acquire.sys 等待 → __syncthreads 后全 block 读）成立。
- padding 行处理：dispatch 对 -1 槽也计数（行块必到 128）、gathered padding 行恒为零、
  combine 索引不引用 padding 槽。闭环正确。
- barrier 生命周期：row0 计数器本卡写本卡清（同 stream 序），slot 行单调 seq 免复位；
  每个 sweep 点新建 scheme/barrier，seq 从零一致。
- group::store 行映射修复（store_strip 置换）与 01/03 的对拍结果自洽。

## 2. 公平性总评

| 维度 | 判定 |
|---|---|
| 精度 | ✅ bf16 vs bf16 |
| 通信真实性 | ✅ 双方都是真跨卡（NCCL vs P2P/TMA），同一卡组 |
| 计时方法 | ✅ 双方 eager、同 warmup/iters、max-across-ranks |
| buffer 预分配 | ✅ 双方都允许 setup 预分配 |
| routing/metadata | ❌ serial 每 iter 做，TK 挪到 setup —— **当前最大不公平项（利 TK）** |
| padding 计算量 | ⚠️ TK 多算 ~2× GEMM 行（不利 TK），latency 口径下自动体现 |
| 权重布局预处理 | ✅ 双方各用各的最优布局，等价于部署期转换 |

结论：**除 routing 口径外基本公平**。"7146µs vs 7062µs 打平"这句话的准确表述是：
"在 routing 成本外置的前提下打平"。

## 3. 下一步优化方向（按测量证据排序）

依据：probe（push 51 GB/s vs pull 弱卡 ~20 GB/s；**远端原子实测可用**）、Phase 2
（dispatch-bound，时延 ∝ 1/comm_sms）、Phase 3b（combine pull 已到 32~49 GB/s 接近带宽顶）。

**#1 dispatch 反转为源端 push（预期收益最大）**
Phase 2 的瓶颈正好踩在本机最弱的路径（SM pull）上。probe 证明远端原子可用 →
12 篇"红线 2"在本机不成立，可以直接：源卡按 schedule 把自己的 token **TMA push** 到
expert 卡的 gathered 槽位 + `red.release.sys` 远端计数（gate 自旋逻辑不变）。
叠加 **P3 的 (token,rank) 去重**（push 一份到 staging，expert 卡本地 scatter 到多 slot）。
账：4096 assignments×14KB=57MB pull@~20 → ~2.9ms；1800 unique×14KB=26MB push@51 →
**~0.5ms**。一项优化拿 ~6×。
（保留 pull 版做回退——换机器 nativeAtomics=0 时退回。）

**#2 FP8 传输**（dispatch 与 combine 各再减半；combine 已贴带宽顶，fp8 是它唯一的大杠杆）
先只做"传输 fp8、GEMM 入口反量化为 bf16"，mma 换 fp8 是第二步。

**#3 schedule 上 GPU 并计入 run()**（公平性 + 生产必需，见 P1）

**#4 padding**：512 token 档把 ROW_BLOCK 降到 64（tile 64×128，warp mma 无障碍）或
per-expert 变长尾块，GEMM 行数省 ~35%。大 token 档无所谓。

**#5 combine 侧工程项**：persistent combine worker 消 HOL；由于远端原子可用，也可试
A' 推式（expert 卡加权后 red.f32 推源卡 fp32 buffer），与 B' pull 对测取优。

**#6 dispatch 深流水**（每 block 多 outstanding TMA）——若 #1 落地则此项自动消失。

**账（4 卡 512 token/rank 目标）**：L0 0.5ms（#1）+ L1 1.7ms（fp8 后 ~0.9ms）+ GEMM 被
隐藏 + act/杂项 0.3ms → **~2.5–3.5ms vs serial 7ms ≈ 2 倍以上**，且 serial-fp8 的通信
不变，优势可保持。

**扩展性提醒**：目前全部数字来自 NUMA node1 的 4 卡 PIX 组。上 8/16 卡前先用 probe 扫
跨 switch / 跨 NUMA 的对（pull 不对称大概率更糟，nativeAtomics 是否跨 root 仍为 1 也要
重测），拓扑分组调度（12 篇 §4.4）会从"提醒"变成"必做"。
