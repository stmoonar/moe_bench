# 实现架构

## 1. 为什么选择 TP 形态

TP 按 intermediate 维切分，每卡持有全部 expert 的一个权重薄片。与 EP 相比，这决定了：

- L0 是稠密 token AllGather，每个唯一 token 跨卡只搬一次，随后在本卡服务其全部 TopK expert；
- TopK expert 的 L1 局部结果可以先在本卡完成预归约；
- L1 跨卡阶段是稠密 ReduceScatter，每卡向每个源 rank 返回一行 partial；
- 调度布局主要是本地消费顺序，不需要像 EP 一样跨卡对齐 expert slot。

主实现位于 `tk_tp_scheme.py`、`kernels/tk/tk_moe.cu` 和
`kernels/tileoverlap/common/sm120_common.cuh`。后者是 GEMM 模板正本；
`kernels/tk/sm120_common.cuh` 是构建时复制的产物，不能直接修改。

## 2. 完整数据流

```text
本 rank bf16 tokens
  └─ rowgroup_quant_fp8（1×128）
      └─ L0: FP8 token/scales AllGather + 本地 scatter
          ⊕ FP8 W1 grouped GEMM
          └─ FP32 accumulator 上直接 SwiGLU，写 bf16 act
              └─ rowgroup_quant_fp8（1×128）
                  └─ L1: FP8 W2 grouped GEMM
                      ⊕ 本卡 TopK 加权预归约
                      ⊕ partial 按源 rank 细粒度 push
                          └─ 水位到齐后本地 final reduce
                              └─ 本 rank bf16 output
```

这不是把 GEMM 切成 chunk 后放到不同 stream 的降级 overlap。通信 gate、完成 epilogue 和角色
转岗嵌在 persistent kernel 内，标准 grouped GEMM 主体保持连续 tile 流水。

## 3. L0：AllGather 与 W1/SwiGLU

- 源端 token 按 K 维每 128 元素量化为 E4M3，scale 为 FP32；线上每 token 从 8KB BF16
  降为约 4.125KB（FP8 data + scales）。
- 数据方向是**源端 push（posted write）**：每张卡按 `push_order`（该源在目的卡上的消费
  顺序）把自己的 token 行直接写进 3 个 peer 的 staging plane——每个 plane 只有一个源卡
  写，无需原子——写完发 per-token 的 `st.release.sys` 到达 flag。peer pull 版本已判负，
  原因见 [07_细粒度通算overlap实验总结.md](07_细粒度通算overlap实验总结.md)。
- 收端 comm block 按 `pull_order`（最早消费 slot 决定的顺序）领 token：本地 acquire 等
  到达 flag，只读**本地** staging，散到该 token 的 TOP_K 个 gathered slot，每散完一个
  就给对应行块计数 +1。GEMM 按相同的 expert-major 顺序 claim 工作，避免“数据到了但不是
  下一块要消费的数据”。
- comm block 中前 `TK_L0_PUSH_SMS` 个做 push，其余做本地 scatter。GEMM 使用全局原子
  dispenser 和共享内存描述环；comm block 干完自己的活后通过专用 named barrier 转岗参加
  GEMM，减少固定占用 SM 的让渡税。
- W1 在 GLU 交织布局上重量化，128×128 scale block 与 FP8 tile 对齐；FP32 accumulator
  直接计算 `silu(gate) * up`，避免独立 SwiGLU kernel 和额外读写。

## 4. L1：W2、预归约与 ReduceScatter

- act 使用同一个 `rowgroup_quant_fp8`，W2 原布局和 scale 可直接用于 `mma_ABt`，无需 W1
  那样的二次布局转换。
- W2 grouped GEMM 产出 BF16 expert output；本卡按 `(src_rank, token)` 汇总本 rank 上的
  TopK partial，FP32 加权、BF16 传输。
- job block 在对应行块就绪后立即把 partial TMA push 到源 rank 独占平面；数据传输与 W2
  GEMM 同一 persistent grid 内并发。
- 每个目的 rank 的本地计数达到 host 预算后，唯一线程发布跨卡水位。源 rank 的 final
  reduce 只等待实际有贡献的 rank，随后本地求和。

L1 默认保持 M 维 v1 方案。“按 N 维分解”在本 PCIe+SM 驱动平台已经实测为负结果，原因见
[04_平台边界与负结果.md](04_平台边界与负结果.md)。

## 5. PCIe-safe 完成协议

协议统一为：

1. 多个生产线程完成数据写；
2. 只在本 GPU 上执行 `atom.acq_rel.gpu` 计数；
3. 达到预计算期望值的线程成为唯一写者；
4. `fence.sys` 后对 peer 独占 signal slot 执行 `st.release.sys`，写单调 seq；
5. 消费端只在本地用 acquire load 自旋等待已知 signal。

它避免了高并发 PCIe 远端原子 RMW 丢增量，也避免跨迭代 reset 竞争。细粒度事件先在本地
聚合，再跨卡只发一次信号；L0 的到达 flag、L1 的水位信号都复用这一模式。

## 6. 调度与资源分工

- GPU schedule builder 在 `run()` 内执行并计时；host builder 是逐元素 golden。
- 常驻块通过 dispenser 获取工作；block-per-job 在大共享内存下会造成 wave 排队，不采用。
- 工作粒度至少要覆盖一次高效 PCIe 操作。1 token×1KB、每次都 wait 会暴露约 1.5~2µs RTT；
  需要组批或水位聚合。
- barrier 角色必须显式分配。`__syncthreads()` 使用 barrier 0，不能和 TK consumer group
  对同一 barrier 的不同计数混用；角色汇合使用专用 named barrier。

## 7. 已定案的实验路径：通信 warp 化（方案A）

历史开关 `TK_L0_WARP=1` / `TK_L1_WARP=1` 曾把 comm 角色从整块 SM 降为 GEMM 块内
producer warp（warp 8）的闲置 lane 1..31：GEMM 拿满全部 SM，通信只花该 warp 的
发射槽，目标是回收让渡税（L0 fp8 口径 ~264µs）而不牺牲 token 粒度流水。协议
（pull_order/行块计数/选举/watermark）与默认路径逐字节同构，只改变执行者。

实测结论已定案为负：peer TMA 与本地 GEMM tile load 共用同一 SM 的 TMA 队列，产生
per-SM head-of-line blocking，1 lane/SM 即有 +175µs 共存税，详见
[04_平台边界与负结果.md](04_平台边界与负结果.md)。当前默认路径（专职通信 SM +
完成后转岗）未受影响。裁决过程与探针数据见
[07_细粒度通算overlap实验总结.md](07_细粒度通算overlap实验总结.md) 第 3 节；
对应代码已随 slim 分支移除，复现需检出 `fp8_tp` 或 `comm_warp` 分支的历史提交。

## 8. 精度边界

- FP8 GEMM 使用 E4M3 输入/权重、FP32 accumulator、per-128K 重标定。
- push/combine/final reduce 保持 BF16 传输与 FP32 局部累加，避免把归约误差进一步放大。
- SM120 工作站芯片上 FP8+FP32 accumulator 的指令吞吐存在平台税，相对 BF16
  baseline 的 GEMM 耗时实测约降低 21.9%~25.4%，而不是理论 50%；当前差异化收益
  主要来自字节减半和融合调度。
