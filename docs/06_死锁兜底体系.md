# 死锁兜底体系：从"整机 wedge"到"有界失败"

2026-07-17 整理。背景：2026-07-16 两次 wedge 事故（P2.5 首测、08p25 步）与
docs/04 坑索引。本文回答两个问题：**这套兜底保证了什么、保证不了什么**，
以及每一层的实现位置。

## 1. 威胁模型

事故链（docs/04 已取证的形态）：

```
协议 bug / 一个 rank 先死
  → 幸存 rank 的持久 kernel 无界等待（自旋 / mbarrier）
  → kernel 不可抢占，超时 kill 只能让进程进 D 态
  → 上下文销毁 / IPC unmap 抱着 RM GPU 组锁永不返回
  → nvidia-smi、新 CUDA 进程、其他容器全部排队 → 整机只能重启
```

关键认识：**这里没有"持锁不放"的互斥锁**。所有跨卡同步都是单写者信号
（seq slot / flag / 计数器），等待方等的是生产者的一次 posted write。
生产者死了，等待方唯一的病症就是"等不到"，因此**把每一个等待点有界化，
就能把死锁从不可恢复事故降级为 ≤~40s 的干净失败**。

## 2. 四层兜底（2026-07-17 全量落地）

### 第 1 层：设备侧自旋有界（PCIE_SPIN_GUARD）

- 位置：`kernels/tileoverlap/common/sm120_common.cuh` 正本宏；
  覆盖 wait_slot / pcie_barrier_all / 全部 GEMM gate / CE flag poll /
  scatter_lane / scatter_warp / tileoverlap02 dispatch_gate。
- 机理：5e8 次 `nanosleep(64)` ≈ 32s 超时 → `trap;` 杀**整个 kernel**
  （所有 block，包括卡在 `__syncthreads`/named barrier 上的线程）→
  CUDA error → 进程退出。
- 成本：miss 路径一次寄存器自增，就绪路径零指令。

### 第 2 层：设备侧 mbarrier 有界（pcie_sync::guarded_wait）

- 动机（第 1 层的审计缝隙）：跨卡 TMA pull（`tma::load_async` 读对端
  `pre_tokens[src_dev]`）喂的 semaphore，对端 rank 死亡时永不 arrive，
  裸 `wait()` 无界挂死。多数场景有传染性覆盖（mbarrier 卡住 → 行块计数
  不涨 → 带 guard 的 gate 饿死 trap 连带杀全 kernel），**但所有 gate 已过、
  只剩尾部 dispatch/comm 块挂在对端 TMA 上时覆盖失效**。
- 实现：`guarded_wait` = `kittens::try_wait`（硬件挂起等待，唤醒延迟与
  `wait()` 相同）+ `clock64()` 计时 1e11 周期（2.5GHz 下 ~40s）超时 trap。
  就绪路径只多一次 clock64 读。
- 覆盖：`kernels/tk/tk_moe.cu` 全部 14 处 token/comm semaphore 等待、
  `tileoverlap/02` dispatch 的 token_arrived。**本地流水线 mbarrier
  （GEMM inputs_arrived/task_ready 等）保留裸 wait**——生产者在同 kernel
  内，任何饿死都会经 gate trap 连带回收，且那是最热路径。

### 第 3 层：host 侧 fail-fast（_fail_fast_exit）

- 动机：kernel trap 后 worker 收到 CUDA error，原 `finally` 还会执行
  `torch.cuda.synchronize()` + `dist.destroy_process_group()`——NCCL 销毁
  要跟（可能已死的）对端握手，teardown 要逐个 IPC unmap / 销毁 context，
  正是 2026-07-16 取证中排队在 RM/uvm 锁后面的调用类别。
- 实现：`distributed.py` worker 异常路径打印 traceback 后 `os._exit(1)`，
  跳过全部用户态 teardown，让内核态驱动统一回收；mp.spawn 按非零退出码
  收割其余 rank。成功路径仍走优雅退出。

### 第 4 层：故障注入验证（tools/fault_inject_kill_rank.py）

- 用法（GPU 机器，单步/单 case 运行，红线第 3 条）：

  ```bash
  python moe_bench/tools/fault_inject_kill_rank.py \
      --kill-rank 2 --delay 10 --timeout 120 --gpus 0,1,2,3 -- \
      python -m moe_bench.bench --config moe_bench/configs/tp_rtx_pro5000_4gpu_fp8.yaml \
      --distributed --scheme tk_tp
  ```

- 断言链：SIGKILL 一个 rank → 其余进程树 `--timeout` 内退净（无 D 态残留）
  → `nvidia-smi` 限时返回 → 每张测试卡能新建 context 跑小 kernel。
- 注意：本测试就是在人为制造故障，跑之前确认卡空闲、接受失败时可能要按
  docs/04 流程恢复。**兜底体系在此测试通过之前只有静态审计背书。**

## 3. 边界：这套体系保证不了什么

1. **host/driver 层不受保护**。RM GPU 组锁是全局的：若元凶在驱动层面
   （teardown 竞态、Xid 后的 RM 状态机），device 侧任何机制都无济于事。
   guard 能做的是让 kernel 侧永远不成为那个"卡死持有者"。
2. **trap 前的 ≤40s 窗口**内，幸存 rank 仍会经 IPC 读已死上下文的显存
   （TMA/LSU posted read）。该窗口能否 wedge RM 未被证伪——这正是第 4 层
   要验证的。
3. `tma::store_async_wait()`（bulk 写提交等待）无界。写到已 unmap 的对端
   通常表现为 fault/Xid 而非挂死，暂不处理；若故障注入观察到挂死在此，
   再补 bulk 写侧兜底。
4. 结论口径：**"死锁有界 + 可诊断 + 卡可复用"是目标；"保证整机不再
   wedge"任何 device 侧机制都给不出**（见 docs/04）。
