# 方案A：通信 warp 化（TK_L0_WARP / TK_L1_WARP）设计与落地

日期：2026-07-16　分支：`comm_warp`（自 `fp8_tp` 切出）
状态：**已定位定案（tp_run_20260716_070406）——机制②共存税坐实（per-SM TMA 队列），
机制①排除；方案A 现形态判负，唯一残余方向 = 非 TMA 拉取绕开队列**

**机制裁决**：机制①（发射饥饿→straggler→gate 车队）排除——gate 税≈0；
机制②（per-SM TMA 队列 HoL）坐实——µs 级 PCIe peer 读占住本 SM 的 TMA 队列，
堵住 GEMM 流水的 A/B tile 加载，且严格随 comm lane 数单调。默认路径的 comm 块
同样发 peer TMA 却不拖慢 GEMM（+183 里主体是 24 SM 让渡），证明这是
**per-SM 资源争用而非全局 L2/PCIe 干扰**——平台事实：**在本机把 peer TMA
拉取塞进 dense GEMM 的 SM，比让渡整块 SM 更贵**。

其他：e2e 双稳（063155 轮 med 3443）在 lockstep diag 下不复现——慢态需要
rank 漂移反馈参与（快态账吻合：964−935≈+29 ≈ e2e min 差 +36）；结构税已
足够判负，双稳不再单独追。l0_warp_s1（917）是唯一小幅正信号（比默认快 18），
但拉取人手减到 110 并发在漂移环境下的稳健性存疑，不作为方向。

### 机制假设（待复跑 + nsys 裁决）

1. **L1 +188µs（稳定，机制基本清楚）**：GEMM 期间推流人手从 24 块×288 线程降到
   110×31 lane（且每 job 的 prered 由 31 线程做，单 job 慢 ~8×），流推速率约减半；
   GEMM 满 SM 的提速（399→~313 估算）不足以抵消排空尾巴的增长。L1 本来就被
   docs/35 判为"v1 近最优、可藏的只有 wire"，方案A 在 L1 上大概率是负结果定案。
2. **L0 双稳（两个候选机制）**：
   a. *发射饥饿车队*：满负荷 mma 的 SM 上 warp 8 拿不到发射槽 → 该 SM comm lane
      已领取的 token 成为 straggler → 卡住其行块 gate → 最多 32 个 SM 停等 →
      车队效应；严重度取决于调度交错 → 进程级双稳。
   b. *TMA 队列 HoL*：comm lane 的 peer pull（µs 级 PCIe 延迟）与 producer 的
      本地 A/B tile 加载共享同一 SM 的 TMA 队列，慢 pull 阻塞流水加载 →
      GEMM 全局变慢。旧 comm 块方案里两者天然在不同 SM 上，无此耦合。
   两个机制都指向同一结论：**同 SM 混跑时，通信与计算的资源耦合从"SM 数"
   变成了"发射槽 + TMA 队列"，后者不是零成本**。min=1745（仅 +36µs）说明
   快态下方案A 的账基本成立，问题是快态不可靠。

### 定案后的处置（2026-07-16）

- **L1 warp 判负定案**：融合税 +301 vs 默认 +173，无翻盘自由度（prered 的 LSU
  工作放上 GEMM SM + 人手减半双输）。TK_L1_WARP 默认 0，负结果入 docs/04。
- **L0 warp 现形态判负**：964 vs 默认 935。共存税是 per-SM TMA 队列结构税，
  调 lane 数/并发治不了（1 lane 即 +175）。
- **唯一残余方向（未验证）**：comm lane 改**非 TMA 普通向量加载**拉取 peer 行
  （ld.global float4，绕开本 SM TMA 队列）。定量前提：若共存税因此归零到
  ~±30µs，L0 融合可到 ~790 vs 默认 935（−145µs，e2e ~1560）。风险：128 深
  outstanding global load 走 LSU/MSHR，可能换一种争用；值不值得做由这 145µs
  的预期决定。
- e2e 双稳不再单独追（lockstep 不复现 + 结构税已定案）。若做向量加载实验，
  必须带 e2e 04w8 复跑验证漂移环境下的稳健性。

## 1. 动机：让渡税不是结构税

当前融合架构把通信角色实现为**整块 SM**（L0/L1 各占 `TK_COMM_SMS=24` 个 comm block）。
归因账（docs/42、bf16 时代 docs/30）显示：

- L0 的暴露 ≈ 100% 是 SM 让渡（fp8 口径 ~264µs）：AG 数据等待本身 ≈ 0，代价全部来自
  GEMM 少了 24 个 SM；
- L1 让渡 +142µs（bf16 实测），另有 ~48µs 真实协议尾。

但 comm block 的实际工作是**异步 DMA 编排**：领 token → 发 TMA → 等 mbarrier → 发
scatter → red.add 计数。全程没有算术指令在关键路径上，90% 时间在自旋。它需要的是
发射槽和内存队列，不是整个 SM 的算力。docs/35 的"L1 GEMM 是 SM-bound → 重叠是 SM
零和"结论，前提是通信以 SM 为粒度占资源；把粒度降到 warp，零和的分母 S 被拿掉。

CE 路线（docs/43/44）试图归零 SM 占用但判负，输在**粒度**：CE 把 token 级消费序流水
退化成分片大块搬运。方案A 保持 token 粒度和 SM 驱动的细流水，只改变"谁在跑这段代码"。

## 2. 关键实现选择：征用 producer warp 的闲置 lane

fp8 dispenser GEMM（`grouped_gemm_sm120_fp8_dispenser`）的 warp 分工：

- warp 0..7：consumer（mma 主力，barrier 0/1 上按 256 计数循环）；
- warp 8：producer，**只有 lane 0 在发 TMA**；lane 1..31 参与完函数内唯一一次全员
  `__syncthreads` 后直接从函数返回，天然闲置。

方案A 把通信放到 warp 8 的 lane 1..31 上，而不是加第 10 个 warp：

| 方案 | 线程数 | 寄存器上限 | GEMM 模板改动 |
|---|---|---|---|
| +1 comm warp | 288→320 | 227→204 regs/thread（fp8 consumer 用量 ~190-210，**有溢出风险**） | 需要 early-return 支持 |
| 征用 producer lane 1..31（采用） | 288 不变 | 不变 | **零改动** |

代价是 warp 8 内 lane 0（GEMM producer 循环）与 lane 1..31（通信循环）永久分歧，
依赖 sm120 ITS（独立线程调度）并发推进。producer 每 stage 只发几条 TMA 指令，其余
时间在 mbarrier 自旋（nanosleep 让出发射槽），预计干扰很小——这是上机要裁决的头号
假设（见 §5 风险）。

## 3. 落码内容

### L0（`tpdisp8::kernel_warp` / `moe_tp_dispatch_gemm_fp8_warp`，TK_L0_WARP=1）

- grid = 全部 SM，全为 GEMM 块；`TK_COMM_SMS` 不再参与 L0；
- 每块 warp 8 的 lane 1..4（`WARP_SLOTS=4`）各管一个 in-flight token：
  独立 `atomicAdd` 领取（全局仍按 `pull_order` 消费序）、专属 smem 槽 + semaphore，
  **无任何 warp 内同步**；
- 数据面与 `dispatch_persistent`（CE=false）逐字节同构：TMA pull fp8 行+scale 行
  （一个 mbarrier 两个 TMA）→ 本地 scatter 到 TOP_K 槽 → `red.release.gpu` 行块计数；
  `dispatch_gate`/`slack`/reset 协议不变；
- 并发深度 4×~110 = 440 in-flight，与现役 24 块×20 lane = 480 同量级；
- smem：GEMM 3×16KB 流水区之后放 4×(4KB+128B) comm 槽，总 ~66KB < 99KB；
- semaphore 在进 dispenser 前 init，由 dispenser 内部全员 `__syncthreads` 发布；
  此后 comm lane 不再触碰任何块级 barrier（barrier 0/1 是 consumer 的 256 计数循环，
  混计数并发到达是 UB，docs/24）。

### L1（`tppr8::kernel_warp` / `moe_tp_gemm_prered_push_fp8_warp`，TK_L1_WARP=1）

- grid = 全部 SM 跑 fp8 W2 dispenser GEMM；`TK_COMM_SMS_L1` 不再参与；
- 排空 = 两个独立团队从同一个 `job_next` dispenser 领 job（每 job 恰好领一次）：
  - **comm 团队** = warp 8 lane 1..31（31 线程），GEMM 全程在其下按 `job_order`
    就绪序流推；同步用 `__syncwarp(0xFFFFFFFE)`（掩码排除仍在 producer 循环的 lane 0）；
    专属 8KB smem 行在 GEMM 流水区之后；
  - **GEMM 排空团队** = 8 个 consumer warp（256 线程），GEMM 出完后在 named barrier 2
    （256 计数）汇合，复用已排空的流水区放 smem 行。**不能用 `__syncthreads`**（它是
    barrier 0 全员计数，comm 团队还在跑 + consumer 曾按 256 计数循环 barrier 0）；
  - producer lane 0 出 GEMM 后直接收工；
- `push_job_team<NT, Sync>` 与 v1 `push_job` 逐行同构：wait_slot 行块就绪 → fp32
  加权求和 8 条 expert_out 行 → TMA 推源卡 staging → 本地选举 + watermark。
  `signal_epilogue`/`final_reduce_push` 零改动。

### scheme / 脚本

- `tk_tp_scheme.py`：`TK_L0_WARP` / `TK_L1_WARP` 开关（默认 0，与 CE 互斥，L1 warp
  要求 `TK_L1_FP8=1`）；新增 `pull_next` 计数器（每迭代清零）；
- `tools/run_tp_all.sh`：`03w8_correct_tktp_fp8_warp`（双开正确性门）+
  `04w8_bench_{l0warp,l1warp,bothwarp}_512` / `04w8_bench_bothwarp_t1024`
  （A/B 阶梯独立定价，非 REUSE 分支）。

## 4. 预期账

- 可回收上限 = L0 让渡 ~264µs + L1 让渡份额（fp8 口径待 08 归因），减去新引入的
  发射槽/LSU 争用；
- e2e 目标：1708 → ~1500-1550（若让渡税大头兑现）；低于按"让渡税是结构税"推的
  ~1660 平台上限。

## 5. 风险与裁决点（上机顺序）

1. **正确性门（03w8）**：协议同构，主要验证 ITS 分歧下的 mbarrier/TMA 行为；
2. **producer 干扰**：04w8 L0 档 vs 04f8 基线,若 GEMM-alone 变慢 >2%,说明 warp 8
   分歧干扰了 producer 发射,考虑 comm lane 加长 nanosleep 或减 WARP_SLOTS;
3. **pull 并发是否够**：440 vs 480 in-flight;若 L0 暴露回升,把 `WARP_SLOTS` 提到
   6~8(smem 还有 ~30KB 余量);
4. **L1 推流人手**：GEMM 期间 31 线程/块 × 110 块 vs 现役 24 块 × 288 线程,总加载
   发射能力约一半;wire 是瓶颈时无影响,若 L1 尾回升看 08 归因;
5. 08 归因工具（time_tp_stages）尚未感知 warp 模式，首轮先用 e2e A/B 阶梯定价。

## 6. 回滚

`TK_L0_WARP=0 TK_L1_WARP=0`（默认）即回 `fp8_tp` 收官形态；两开关相互独立，可单开
定价。判负则按惯例把结论沉淀进 docs/04 后关档。
