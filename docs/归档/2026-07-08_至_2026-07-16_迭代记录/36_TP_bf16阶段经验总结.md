# 36 TP bf16 阶段经验总结(第 1~15 轮,fp8 前的知识底座)

> bf16 阶段收官:**主形状 NE=64/T=512 = 2116µs vs serial 2624 = 1.21×**
> (L0 v2+GLU + L1 v1),T=1024 1.33×(3781 vs 5020)。本篇把 15 轮的
> 结论按"平台事实 / 调度结构 / 协议 / 方法论 / 负结果"五类整理,
> 是 fp8 阶段(docs/37)与未来移植的知识底座。

## 1. 平台事实(sm120 × PCIe,全部实测)

| 事实 | 数值/结论 | 出处 |

| L0/L1 GEMM 都是 SM-bound | alone@110 → fused@86 按 110/86 缩放吻合 | docs/30/34 |
| comm 对计算的拖慢 ≈ 纯 SM 让渡 | L0 +26% vs 模型 +27.9%,数据等待≈0 | docs/30 |
| pull 弱路径 / push 强路径 | 23.5GB/s vs 50.9GB/s(4 SM 打满) | docs/22(mb) |

## 2. 有效的调度结构(按收益排序)

1. **拉取/到达序对齐消费序**(docs/20,+37%):pull_order 按 min-slot
   (expert-major),GEMM 沿同序消费 → 数据等待归零。反模式:ring 序/
   "本地优先"(块内混所有源,本地先到毫无用处)。
2. **comm 块转岗**(docs/30/31,−68µs):dispenser 化 GEMM(全局原子发放
   + smem 描述环,流水跨 task 连续),comm 块拉完 AG 经 bar.sync 2 加入
   GEMM。L1 反向早已有之(comp 块算完转岗排空 push)。
3. **SwiGLU 融进 GEMM epilogue**(docs/30/31,−83µs):权重列交织
   [gate64|up64],fp32 累加器上算 silu(gate)*up 直存 act;GEMM 级零开销
   (969 vs 978),精度反而更好。**fp8 阶段的 act 量化应沿用此挂点**。
4. **全员 dispenser + 常驻块**(docs/20):block-per-job 是反模式(大
   smem 下按块排队 = 粒度串行);常驻块 + 原子 claim + 就绪序。
5. **工作粒度 = 一次高效通信的最小单位**(docs/33):1 token×1KB 的
   push job(每 job 一次 TMA+wait)让 PCIe 延迟暴露 16384 次;16-token
   组批(16 发 1 等)回收 84%。

## 3. 协议纪律(PCIe-safe 三件套)

- 跨卡完成检测:**本地 atom.acq_rel 选举 + 单写者 st.release.sys + 本地
  自旋**;序号化(seq 单调)免 reset;
- named barrier 盘点先行:__syncthreads=bar0,与 GEMM consumer group 的
  256-count 并发混用 = UB(docs/24);角色汇合用专用 bar.sync 2;
- 信号聚合:细粒度完成事件本地计数聚合,跨卡信号只发一次(列扫计数、
  chunk 水位、GRP 选举都是同一个模式)。

## 4. 方法论(踩出来的流程)

- **公平口径先行**:sched/量化等每步成本必须计入 run()(漏计 sched 曾
  虚报 1.48×);serial 基线的调优状态要显式管理(00_reset_tuned_cfg);
- **分阶段归因工具是第一生产力**:time_tp_stages 的 fused/alone/nb/cm
  多参考对照,把每轮改动的账拆到 ±10µs;新增优化必配隔离探针;
- **A/B 阶梯**:每项优化独立开关(TK_L0/TK_L0_GLU/TK_L1/...),脚本里
  独立门与 bench,失败可二分,收益可定价;
- **CPU 预检 + host/GPU 双 builder 对拍**:上机前抓逻辑错误(builder
  逐元素 + 数据流仿真),零 GPU 依赖;
- **FOCUS/STEPS 过滤**:迭代验证 ~4 分钟;全量回归留里程碑;
- **预期账先写后验**:每轮 docs 先写预期数字,实测对账,偏差本身就是
  归因线索(第十三轮 +603 的模型对账直接锁定粒度病);
- **正本意识**:kernels/tk/sm120_common.cuh 是构建产物,改模板改正本
  (kernels/tileoverlap/common/)。

## 5. 负结果(同样是资产)

- **L1 N 维分解(Comet layer1-N)在本平台不成立**(docs/32~35):
  三轮证据链(协议对、粒度病修复后仍 −95µs、换序无罪、小预算单调反向)。
  根因:Comet-N 的前提是通信不占 SM(NVLink/copy engine);PCIe + SM
  驱动推送下重叠是 SM 零和,v1"全速 GEMM + 全员后排空"已近最优。
  **依赖分解的正确维度不只看数据流,还要看通信引擎是否消耗计算资源**;
- push dispatch(L0)冻结:GEMM-bound 下 mb 带宽差不在关键路径(docs/25);
- L1 减 comm 预算(v1)证伪:comm 块是有效推流工(docs/31);
- sched 合并 all_gather 倒贴 +20µs:省一次 NCCL 启动 < 引入的 strided
  copy;µs 级优化先算搬运账(docs/31);
- ROW_BLOCK=64 仅 NE=256 净赢:padding 本以满效率算(docs/16)。
