# 03 SM 间调度与资源分配

> 主题：通信占多少 SM、计算与通信怎么在 grid 层面分工、tile 以什么顺序执行。

## 1. 通信到底需要多少 SM（经验数字汇总）

| 场景 | SM 数 | 来源 |
|---|---|---|
| 跨节点 all-to-all（IB+NVLink 转发，训练） | 20/132（10 channel）；新一代降到 4~6 | DeepSeek-V3 / DeepEP |
| 节点内 AllReduce+RMSNorm（multimem/NVLS） | 2~8（4~8 已打满，>8 无增益；旧方案 16~20） | TokenWeave |
| 跨节点 GEMM+RS 的一级归约 | 15~16（按 ≥470GB/s 归约带宽解析算出） | TileLink |
| MoE combine 方向的专职通信 CTA | 18~46 随 shape 变化（开源版固定 28/132） | Comet |
| counting/wait kernel | 1 block 1 thread（占 1 个 SM） | FlashOverlap |
| copy engine / NIC 后台路径 | **0** | DeepEP LL hook、MSCCL++ PortChannel、Flux AG host copy |
| 反面基准：NCCL 默认并发 | 16+ SM，导致并发 GEMM 慢 15~20% | ISO 实测 |

三条推论：

1. **打满链路所需的 SM 远比直觉少**——先按带宽解析估算（目标带宽 ÷ 单 SM 可发起的有效带宽），再实测回退，不要拍脑袋给 25%。
2. **能不用 SM 就不用 SM**：copy engine、NIC 后台、NVSwitch 在网归约都是 0 SM 或近 0 SM 的通信执行体；SM 只应该干"必须由 SM 干"的事（细粒度控制、gather/scatter、就地归约）。
3. **通信 SM 数应是运行时一级参数**，不能编译期写死（Comet 开源版把它烧进模板常量，导致自适应能力退化，是反面教材；DeepEP 的做法——类级参数 + 解析式默认值 + 手动覆盖——是正面教材）。

## 2. grid 层面的三种分工形态（按侵入性排序）

1. **分 kernel 分 stream**：计算 kernel 与通信 kernel 各自独立（FlashOverlap、DeepEP normal、TileLink 非融合形态）。要点：通信 stream 用高优先级（否则拿不到 SM，重叠窗口白白流失）；计算 kernel 对应缩小 grid 或接受 wave 数 +1 的建模修正。
2. **同 kernel 内 block 静态分角色**（Comet、TK）：grid 末尾 N 个 CTA 走通信分支，其余走计算分支。要点：两类 CTA 的 smem/寄存器需求独立（通信 CTA reinterpret 复用同一块 smem）；**计数与 CTA 数必须严格自洽**——grid 小于 SM 数时要有补计数机制，空转 CTA 也要参与 arrive，否则 barrier 永远等不齐（Comet 的两处防死锁细节都源于此）。
3. **同 CTA 内附加通信 warp**（Flux SM90 RS 的 DMA warp、TK producer 内加一个通信 warp）：不占额外 CTA，通信逻辑跟随 tile 所有权走。要点：warp 角色化后各自独立循环、共享 mbarrier 环。

选择依据：通信与计算的粒度耦合越紧（如 RS 的 per-tile pull+reduce），越适合形态 3；通信是规整大块搬运，越适合形态 1；MoE 这类"通信本身含 gather/归约计算"的适合形态 2。

## 3. tile swizzle：重叠时序的第一控制手段

**所有成熟工作都不引入新调度器，只改 tile 遍历顺序公式。** 已验证的 swizzle 模式：

1. **consumer-wait 型（AG+GEMM）——本地先算 + 环形推进**：每个 rank 的 CTA 从自己本地 shard 对应的 tile 行开始，环形遍历。首波 tile 零等待；后续 tile 的需求顺序恰好与 ring 拷贝的完成顺序一致，等待时间最小化。多节点版先按 node 再按 local rank 做二维偏移；节点间访问顺序用拉丁方互相错开。
2. **producer-push 型（GEMM+RS）——先算别人的，自己的最后算**：各 rank 加 rank 偏移错开写目标（同一时刻 8 个 rank 写 8 个不同的 GPU，避免写风暴集中在一个 HBM/内存控制器）；且"最终留在本 rank、无需发送的行"排到最后（尾部零暴露通信，CommFuse 量化过：仅此一项通信隐藏率从 83.9% 提到 99.8%）。
3. **到达序驱动型（Syncopate）**：tile 执行序跟随数据/chunk 的实际到达序重排，chunk 内部再做小 swizzle 恢复 L2 局部性——重排会破坏原有 supergrouping 的 L2 命中，必须补偿。
4. **MoE 的 circular shift**：子问题处理顺序 = 从本 rank 开始循环移位，本地 token 排最前。

设计纪律：
- swizzle 函数应是框架的一等公民参数（枚举：无 / rank 偏移 / 拓扑环 / 到达序 / 自定义），可独立于 kernel 替换。
- **swizzle 与拓扑强耦合**：NVSwitch（一次一个 peer 的 ring 序最优）与全互联（必须同时从所有 peer 拉子块）最优顺序完全不同，换硬件必须重新选择。
- raster 方向（沿 M / 沿 N / 启发式）也是调参项，同 shape 不同 layout 的最优选择不同。

## 4. wave 对齐与切分数量

- 切分不是越多越好：**每多切一块 = 多一次 wave 量化损失 + 多一次同步**。TokenWeave 的例子：132 SM 上 300 CTA 的 kernel 是 3 wave；等分两半（150+150）变 2+2=4 wave（变慢）；对齐 wave 边界切成 132+168 则维持 3 wave。
- 因此切分点要**对齐 SM 数（或 wave 容量）的整数倍**；tile 级方案同理——分块导致计算 kernel 尾 wave 利用率下降时，细粒度反而变慢。粗二分 + wave 对齐经常优于 16 路细分。
- 判断顺序：先算 `num_waves = ceil(tile 数 / 单波容量)`；num_waves ≤ 1 直接放弃 tile 级重叠（改 token/seq 切分或不重叠）；num_waves 少（2~4）用粗分段；num_waves 多才有细分空间，同时注意尾波调度。

## 5. 长尾治理

- **全员收尾**：专职通信 CTA 处理前面各段，最后一段由算完的全部计算 CTA 一起做（Comet）——消掉专职通信资源在收尾阶段的带宽瓶颈。
- **首段小、末段小**：首段小让通信尽早启动，末段小让尾部暴露最少（FlashOverlap 的分段剪枝规则）。
- **跨边界/不规则 tile 推迟处理**：依赖多个 rank 的碎 tile 推迟到其依赖的最晚阶段，不让一个碎 tile 阻塞主流水。
- **MoE 负载不均**：expert 倾斜使个别子问题很小/很大——监控 per-expert/per-rank 耗时分布；静态切分（token 段→channel）在极端倾斜下会放大长尾，需要 capacity 上限或动态领任务兜底。

## 6. 与 L2/DRAM 的互动

- 通信数据"只过一遍"，不应驻留缓存：用旁路缓存的读写路径（不驻留 L1、限定 L2 提取粒度），显著降低通信对计算 SM 的 L2 干扰（DeepSeek-V3 的核心手段之一）。
- chunk 大小与 L2 压力直接相关：chunk 太大挤压计算的 L2 工作集，太小打不满 NIC/链路——chunk 尺寸要按集群实测调优（DeepEP 按 EP 规模打表）。
- 写远端时避免"多卡同时写同一目标"（swizzle 错峰）；读远端优先走 TMA/DMA 路径，不经过本地 L2 的读放大。
