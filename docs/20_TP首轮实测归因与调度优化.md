# 20 TP 首轮实测归因与调度优化（pull_order + 全员 dispenser）

> 首轮上机（tp_run_20260711_124839）：正确性全绿、性能全面败于 serial。
> 本文记录归因逻辑与两项结构修复。承接 docs/19。

## 1. 首轮结果（4×RTX Pro 5000, 卡组 9,11,13,15, bf16）

正确性：verify_tp_schedule 全过；NE∈{64,128,256}+skewed 对拍全 ok（rel_err 4.6e-3，与 EP 同量级）。

| T=256 / T=1024 | 1671 / 5024 | 2027 / 6870 | 0.82× / 0.73× |

## 2. 归因（不用 profiler，账就够了）

**证据 1：comm_sms 4→24 改善 1950µs 且未收敛**，同时从 GEMM 拿走 20 个 SM
反而更快 → 瓶颈不是带宽也不是 GEMM，是 comm block 的**排队串行**。

对账：layer1 每 job 一个 block（2048 块，97KB smem → 每 SM 驻一块），
4 个 comm SM = 512 波、24 个 = 86 波，波差 × 每块几 µs ≈ **~1700µs，对上**；
dispatch 只有 171 块，解释不了（≈280µs）。

**证据 2（设计复盘）：两处依赖粒度错误**（experience 十条经验第 1 条）：

- **L0 ring 拉取序**：balanced 下每 expert 的 row block 混多个源，而 ring 序
  逐源排空 → 所有 row block 都等最后一个 ring 段，GEMM 停在整个 AG 后面
  （"本卡先拉"对 row block 完成度毫无帮助——每块都缺远端 token）。
  且逐源排空使 3 条 PCIe 链路串行使用。
- **L1 job 依赖 max slot**：token 的 8 个 expert 散布全表 → 几乎所有 job
  等到 W2 GEMM 尾部才就绪，然后 2048 块在 16 个 SM 上以块调度粒度慢慢排空。

**证据 3：绝对差随 T 线性**（T=256/512/1024 差 356/989/1846µs ≈ 0.45µs/job），
与"job 数 = world×T 的串行排空"一致。

## 3. 修复（本轮已实现，含表裁决）

1. **pull_order（L0）**：拉取序改为按 token 的 **min gathered slot** 排序
   （= expert 主序）。效果：每个 expert 的 token（4 个源交错 → 链路并发）
   先于下一个 expert 拉完，row block 沿拉取前沿逐个就绪，GEMM 边到边算；
   AG 时间本身也因链路并发缩短。表在 host golden + GPU builder 双实现，
   verify_tp_schedule 增加置换+有序不变量。
2. **全员 dispenser（L1，gemm_push_kernel_tp）**：不再每 job 一块。
   grid = comp + comm 常驻块；全部块从原子 dispenser 领 job，经
   **job_order（max-slot 排序 = 就绪序）**：comm block 在 GEMM 期间流式推
   最早就绪的 job（保留边算边推），comp block 跑完 GEMM 任务立即加入排空
   （experience/08 §5"全员收尾"）→ 尾部在 ~110 SM 上排空而不是 num_comm_sms。
   块开销归零（无块churn）。每 job 恰好被领一次，单写者/选举不变量不动。
3. **tools/time_tp_stages.py**：分阶段归因（各阶段 + L0/L1 GEMM-alone 对照，
   直接读出 fused 相对 GEMM 的暴露量），一键脚本 step 08 自动跑
   （默认 comm_sms=16 + 对照组 8）。

## 4. 修复后的预期账（供下轮对数)

- L1: GEMM ~0.8ms + 全员排空 2048 job（~130MB 本地读 + 12.6MB 跨卡推）
  ≈ +100~200µs 尾部 → ~1.0ms。
- L0: AG ~300-600µs（链路并发后）完全藏进 gate+up GEMM ~1.5ms。
- e2e ≈ 1.5 + silu 0.1 + 1.0 + final reduce 0.1 + sched 0.2 ≈ **~2.7-2.9ms**，
  与 serial 2624 相当或略慢。**结构性提醒**：TP serial 的通信只占 ~600/2624
  （23%），完美重叠的理论上限 ≈ 2.2ms（GEMM 受限）——TP 融合收益天花板
  远低于 EP（experience/01 §10 通信占比决定天花板的直接体现）。若本轮
  优化后仍不及 serial，剩余差距应主要在我们 GEMM 模板 vs triton 的效率差
  （time_tp_stages 的 GEMM-alone 会直接给出），而非融合结构。

## 5. 遗留观察

- NE=256 时 tktp min 6370 vs med 10349（首轮 03 对拍）抖动巨大 —— NE=256
  的 P=32768，job 依赖尾部效应放大；本轮修复应显著收敛，若仍抖动查
  dispenser 领取与 GEMM 收尾的竞争。
- serial 在 NE=128/256 明显变慢（3280/5292 vs 2624）：triton fused_experts
  的 per-expert 启动/对齐成本随 NE 增长 —— tktp 的相对机会在大 NE。
