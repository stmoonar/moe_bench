## 2. 首份分阶段归因（NE=64/T=512, comm24, µs, max-over-ranks）

| 阶段 | pull | push | pull@comm8 |
|---|---:|---:|---:|
| sched | 277 | 276 | 275 |
| tok_copy | 30 | 29 | 28 |
| L0_fused | 1231 | 1293 | 1575 |
| silu | 109 | 108 | 111 |
| L1_fused | 695 | 694 | 809 |
| final_red | 21 | 20 | 15 |
| L0_gemm_alone | 977 | 974 | 973 |
| L1_gemm_alone | 509 | 508 | 508 |
| **L0 暴露** | **254** | 319 | 602 |
| **L1 暴露** | **186** | 186 | 301 |

读数：

1. **TK GEMM 比预估快得多**：L0+L1 GEMM-alone = 1486µs（~210 TFLOP/s
   有效吞吐，86 comp SM 下），此前 2.2ms 的预估过悲观——这就是 docs/25 §4
   "实测好于预期账"的直接解释。
2. **sched 277µs 是最大的单项可压缩项**（e2e 的 12%）：两个 NCCL
   all_gather + graph 回放（~30 个 kernel 的 argsort/scatter 链）。本轮已
   做第一刀：pull 路径不再重建 push_order（少一次 argsort）。进一步压缩
   （合并两个 all_gather 为一次、裁剪 builder 链）备选。
3. comm 8→24 的收益按层分解：L0 暴露 −348、L1 暴露 −115——**两层都受益**，
   comm 块同时服务 L0 dispatch 队列与 L1 dispenser 的设计判断成立。
4. push 与 pull 的差全部在 L0 暴露（319 vs 254）：scatter 的 block-per-token
   串行度 > pull 的 12-lane TMA 流水，docs/25 §2 的冻结归因被数据背书。
5. 理论地板 ≈ GEMM 1486 + silu 109 + copy 30 + final 21 + sched(压缩后 ~150)
   + 少量暴露 ≈ **~1900µs（对 serial 2625 为 1.38×）**——剩余可挖 ~400µs。

## 3. 新异常：T=1024 双峰（下轮头号归因项）

T=1024（comm24 默认）：mean 8993 / med 10020 / **min 4210**——min 与上轮
comm16 的 4325 同水平，但中位数 2.4× 慢，明显双峰。上轮 comm16 时稳定。
怀疑方向：T=1024 时 dispatch 短命块 342 个 × comm SM 24 的排队相位、或
L1 dispenser 4096 job 与 GEMM 收尾的间歇性互锁。**不猜了**，脚本已加
06b：comm16/24 对照 bench + T=1024 两档分阶段归因（time_tp_stages 已支持
tokens 参数），下轮数据裁决。

## 4. 下一步（优先级）
