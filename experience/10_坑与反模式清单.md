# 10 坑与反模式清单

> 全部来自论文自述或源码中的真实防御措施。按类别组织，可直接当 code review 清单用。

## A. 死锁面

1. persistent kernel + 跨卡自旋时，任何一张卡的 grid 少驻留一个 CTA = 全体死锁。占用率要逐卡实测（cluster 尺寸会隐性降低可驻留 SM 数：148 SM 芯片 cluster=4 只能激活 132）。
2. barrier 计数必须对"每一个 CTA"精确自洽：grid < SM 数要补 arrive 差值；没拿到任务的空转 CTA 也要补计数；kernel 提前退出前对没轮到的段补 arrive。
3. signal 的发出顺序与 wait 方的遍历顺序必须一致（tile 所有权映射两侧用同一公式）。
4. 两个互相依赖的 kernel 可能一个占满 SM 另一个未被调度而互等——用"调度就绪 flag"+静态 CTA 配额约定解决。
5. 集合通信的分段配置必须全 rank 一致（段数、每段大小、hint 表），否则某 rank 计数永远不达阈值，全 job 挂死；多机配置文件放共享存储。
6. 环形队列的发送窗口必须 ≤ 接收缓冲一半（懒惰 head 回写的前提）；乱改 chunk 参数可能死锁——所有等待带超时+陷阱兜底，慢/死 rank 可屏蔽。
7. 跨 stream 依赖（kernel 等另一条 stream 的 host 拷贝置信号）中，若拷贝未入队或 barrier 顺序错，kernel 永久自旋；PCIe 上 GEMM 若占了高优先级 stream，通信 kernel 拿不到 SM 同样近似卡死。
8. 对称内存分配是集合操作——有 rank 不参与就挂起；析构释放同样要显式集合化。

## B. 内存序与可见性

9. 数据依赖的信号必须 release 写 / acquire 读；relaxed 版本只能用于纯执行顺序同步——误用是"通常也对、偶发出错"的最难查一类 bug。
10. 信号置位必须在异步 store 确认落地之后（先等 store 完成再置 flag）。
11. 跨卡同步的 scope（gpu vs sys）用错 = 偶发不可见的 hang。卡内流水用硬件 mbarrier，跨卡才用 sys scope 原子。
12. 编译器/软件流水会把异步 load 提前越过 wait——wait 与 load 之间要显式建依赖（token 机制）；"漏了通常也对"，必须靠规范而不是测试兜住。
13. 无 fence 的 relaxed 信号在特定架构上碰巧正确（同设备 L2 可见性 + 时序掩盖），移植即隐患——移植前把所有信号路径按严格语义重审。
14. PCIe P2P 的内存序保证弱于 NVLink：为 NVLink 设计的信号协议直接跑在 PCIe P2P 上有乱序风险。
15. 旁路缓存的读指令组合属于架构相关行为（个别是文档外用法），换代/换平台先关闭激进路径再逐项验证。

## C. 信号与缓冲的物理布局

16. 每个 flag 独占 128B cache line + padding；m 小于 tile 时相邻 tile 的 flag 挤同一行 → 自旋+原子混合的 false sharing 代价巨大。
17. 信号复位与下一轮写入之间要 barrier 或 CAS 语义隔离（"两道 barrier 夹住 memset"或"消费即复位"）。
18. 监控/调优模式与运行模式的信号缓冲形状不同——传错即越界；调优模式的额外计数器要手动清。
19. 复用发送缓冲前必须确认在途完成（flush/quiet）；双缓冲意味着同时最多持有 2 份结果，第 3 次调用覆写。
20. 原子加语义的输出缓冲必须零初始化 + 全局 barrier + 流同步——漏掉读到上轮脏数据。

## D. 粒度与调度的反模式

21. **反模式：per-tile 信号起步**。信号从 rank 片/wave group 起步，向下细化要算账。
22. **反模式：每 wave 一段**。看似自然实测平均劣化 17%（仅 4% shape 下最优）——分段必须调。
23. **反模式：等分切分**。不对齐 wave 边界的切分使总 wave 数 +1，全盘变慢。
24. **反模式：为通信切小 GEMM**（TE 式 decomposition）——小 shape 下负收益至 -125%。
25. split-K/stream-K 与"1 tile = 1 信号"互斥（多 block 写一 tile），共用要改计数语义。
26. one-wave shape 上强做 tile 级融合：prologue 等待无人掩盖，还可能因输出行数过少让写出效率崩塌（实测耗时降低 -5.3%）。
27. tile 执行序重排后不做块内 swizzle → L2 局部性被破坏，重排收益被访存回吐。

## E. 资源与干扰

28. "放另一条 stream"≠ 免费：通信库默认占 16+ SM，并发时 GEMM 慢 15~20%；通信 SM 必须显式预算。
29. counting/wait kernel、通信 kernel 各占一个 SM——性能模型里要按 SM−k 修正 wave 数，漏掉则系统性乐观。
30. 通信 stream 不设高优先级 → 拿不到 SM，重叠窗口白流失；PCIe 上还要反过来把 GEMM 压到低优先级。
31. 通信数据驻留 L1/L2 污染计算工作集——用只过一遍的旁路读写 + chunk 尺寸控制 L2 压力。
32. 通信 CTA 数编译期定死（模板常量）→ 自适应能力退化 + 新硬件（SM 数不同）要改硬编码。SM 数、CTA 配额一律运行时参数化。

## F. 动态性与数据类型

33. MoE 每步的 CPU 侧 schedule 重建含 D2H 同步，小 M 时是显著固定开销——路由不变时必须走 handle 缓存路径。
34. host 自旋等接收计数与 CUDA graph 不兼容——低延迟路径用固定上界缓冲绕开。
35. 远端原子归约的数据类型支持不一致（BF16 在旧架构缺失 → 退 FP32 且缓冲×2；FP8 有额外对齐/scale 布局要求：hidden 整除 128、scale 列主序等）。
36. 原子加归约 = 非确定性求和顺序，影响训练可复现性——要么接受并记录容差，要么固定归约顺序。
37. 混合精度累加器（fp16 accumulate）在大 K 下有精度风险，与 fp32 累加基线对比时先对齐口径。
38. shape 整除性约束要在 API 层显式检查（M/N 整除 tile、N 整除分段×列块），静默错误比拒绝执行糟糕得多；pad 策略与 tile 选择的交互（用 pad 前还是 pad 后的 shape 选配置）要写清楚。

## G. 工程与环境

39. 读环境变量决定关键参数（如 rank offset）时，非标准启动方式会静默拿到错值——显式传参优先，环境变量只作默认值。
40. 特定 CUDA 版本 + 特定分配方式的 driver 已知问题（旧版本 NVLink + 对称分配）——底座保留分配路径开关。
41. P2P/跨卡原子能力必须运行时探测 + 自动降级（虚拟化、ACS/IOMMU、消费级 GPU）。
42. 设备特判是常态（个别型号 P2P read 差、SM 数不同）——框架留 per-device 覆盖钩子，不要假设"同架构行为一致"。
43. 依赖库版本敏感（模板库小版本编不过/跑不对）——锁版本并在 CI 里矩阵验证。
44. 频繁 create/destroy event/handle 有累积开销——一律缓存复用。
45. benchmark 假阳性：只看总 latency；不测干扰系数；用峰值带宽估分段通信；不验证完成序确定性。四项都要堵。
