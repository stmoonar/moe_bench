## 2. 但 e2e 只有 T=1024 兑现,T=256/512 反而变差

| 档位 | serial(未调优) | serial_tuned | Δ | kernel 级预期 |
|---|---:|---:|---:|---:|
| T=256 (M=1024) | 1667 | 1680 | **+13 ✗** | −98 |
| T=512 (M=2048) | 2627 | 2671 | **+44 ✗** | −130 |
| T=1024 (M=4096) | 5025 | **4883** | **−142 ✓** | −167 |

tuned 日志 0 次 "Using default MoE config"(config 确实被用上),但小 T 档
被用**错**了。两个候选归因:

1. **查表键错位(主嫌)**:vLLM 实际 lookup 的 M 可能不是 token 数(如按
   M×topk)。若如此,T=256/512/1024 的 lookup(8192/16384/32768)全部就近
   命中我们文件里的 8192 键 → 三档都拿到 `{BM128,BN128,BK64,G16}`——恰是
   M=4096 的赢家。完美解释"只有 T=1024 兑现全额、小 T 拿到不合身 config
   略变差"的模式;
2. **赢家诅咒(次嫌)**:648 选 1、iters=8 的初扫,选中值系统性偏乐观;
   但它只能解释增益缩水,解释不了**变差**。

本地无法读远端 vllm 源码裁决 1,于是让调优器自己裁决(见 §3)。

## 3. v2.1:finalize 终审阶段(不再盲写)

`tune_moe_tp_noray.py` 新增单卡 finalize,初扫只出**入围名单**(每 M
top-4×4 shard,合并 top-6):

- **键映射自校准**:M=1000 探针跑一次 fused_experts,从
  try_get_optimal_moe_config 收到的实参里找 1000(键=M)还是 8000
  (键=M×topk),据此决定写键——两种 fork 行为都自动适配;
- **复审消赢家诅咒**:入围 config + 默认 config 用 iters=30 重测定名次;
- **无净增益档钉死默认**:该 M 档显式写入 vllm 默认 config,防近邻键把
  不合身的 config 漏进来(v2 的文件里小 M 键正是这样被 8192 键污染的,
  如果键映射是 ×topk 的话);
- **端到端自证**:写完文件走真实查表路径(不打 patch)复跑,断言每个 M
  选中的 config 与预期一致 + 耗时与复审值吻合(±3%),任一 WARN 即整步
  FAIL——下一轮 09_tune 的日志会直接给出键映射与 PASS/FAIL 终表。

配套:`run_tp_all.sh` 新增 **00_reset_tuned_cfg**——开跑先删掉已安装的
`E=*,N=768` 调优 config。否则本轮装机的产物会让下一轮 04/06/07 的
"serial" 悄悄变成(还是错键的)调优口径,与历史失去可比性;09 会重新生成。
