# 01 相关工作总览

> 每个工作：定位 → 核心机制 → 关键数字 → 适用边界 → 对我们最有价值的经验。文末有一页对比表。

## 1. Flux（ByteDance，arXiv 2406.06858）

**定位**：TP 场景 GEMM 与集合通信的 tile 级融合库（AG+GEMM、GEMM+RS，及 MoE/序列并行变体），覆盖 A100/L20/H800、NVLink/PCIe/跨节点。

**核心机制**：
- AG+GEMM：通信由 host 在独立 stream 上按 ring/all2all 顺序发 P2P 拷贝，每完成一个 chunk 就用 stream 级写值原语置一个 int32 signal；GEMM kernel 的 prologue 里按"本 tile 覆盖哪些 chunk"自旋等对应 signal。等待收敛到 producer（load）warp，consumer warpgroup 不自旋，等待被 warp specialization 天然隐藏。
- GEMM+RS：Hopper 上是 pull 模式两级握手——每个 CTA 的 epilogue 写完本地结果后置"tile 就绪"flag；同 kernel 内每 CTA 附带一个 32 线程 DMA warp，从远端对称地址拉取属于自己的 tile 到 smem 再本地归约，攒满所有 rank 后（跨节点时）再推给远端节点。
- 通信 chunk（= rank 分片，可再切）与 GEMM tile 解耦，一个 GEMM tile 可跨 2 个 chunk，逐 chunk 等待。
- swizzle 三件套：AG 侧各 rank 从自己本地 shard 对应的 tile 行开始环形推进（首波零等待）；RS 侧各 rank 加 rank 偏移错开写目标，同一时刻不同 rank 写不同 GPU；多节点用拉丁方查表错开节点间访问顺序。
- 不预留 SM 是它的卖点：单个 fused kernel 占满 GPU，等待靠 warp 切换隐藏（PCIe 模式例外，见 07 篇）。

**关键数字**：对 TransformerEngine 加速 1.01~3.25×（PCIe 最大）；重叠效率最高 96%；小 m（64~512）对 TE 优势 1.33~4.68×；端到端训练 1.05~1.24×、prefill 1.45~1.66×。反例：H800 RS 在 m=64 时 0.95× 倒退（m 被 8 rank 切分后 TMA store 行数过少）。

**适用边界**：通信占比 <10% 时收益仅 ~1.05×；tile 数不足一个 wave 时 prologue 等待无法被掩盖；对 P2P/对称内存和拓扑敏感。

**最有价值的经验**：signal 的完整内存序方案（读 acquire 自旋 / 写 fence+release 归约 / CAS 消费即复位）；per-tile flag 必须 128B 对齐 + padding 防 false sharing；comm tile 无普适最优值必须 autotune；"两道全局 barrier 夹住 signal 复位"的生命周期管理。

## 2. Comet（ByteDance，arXiv 2502.19811，MLSys'25；代码并入 flux 仓库）

**定位**：MoE 层（dispatch→expert GEMM→combine）的 tile/子张量级重叠，核心贡献是 shared tensor 依赖分解 + thread-block specialization + 自适应资源分配。

**核心机制**：
- Layer0（通信→计算）沿 **M 维**分解：token 按 (source_rank, expert) 排序，把 nexperts 个 GEMM 问题拆成 nexperts×tp_size 个子问题，每个子问题的依赖收敛为"某一个 rank 的分片已到达"（一个 flag 放行整个子问题）；计算顺序做 circular shift，本地 rank 的 token 排最前（零等待起步）。不能沿 N 分——沿 N 每个 tile 仍依赖全部 rank 的数据。
- Layer1（计算→通信）沿 **N 维**分块：combine 对同一 token 的 topk 行做归约，M 维强耦合；N 维切成 SPLITS 份（7168→7、1152→9、其他→8），GEMM 的 problem 遍历序改成"列块优先"，前几列算完即可启动该列块的 reduce+RS。
- Thread-block specialization：同一 grid 内末尾 28 个 CTA 专职通信（gather topk 行、FP32 累加、写远端对称缓冲或系统级 bf16x2 原子加），其余 CTA 跑标准 CUTLASS cooperative GEMM；smem 由通信 CTA reinterpret 复用，寄存器走 producer 40 / consumer 232 的非对称分配。
- 精巧细节：GEMM CTA 算完不退出、全员回头帮做最后一个 split 的通信（消长尾）；grid 小于 SM 数时由 0 号 CTA 补 arrive 差值防死锁；跨 rank 边界的 tile 推迟到其依赖的最晚 stage 再算。
- 自适应：论文中通信 CTA 数随 shape 变化（M=4096→18，M=16384→26，TP=4→46）；开源版退化为 AOT 编译 variant 笛卡尔积 + 按 (meta, shape) 查 tuning 表。

**关键数字**：单层平均 1.96×、端到端 1.71×、通信隐藏率 86.5%（对比 FasterMoE 29.2%）；M=4096 时 2.37×、M=16384 时 1.28×——**小 batch 收益更大**；生产万卡部署，节省数百万 GPU 小时。

**适用边界**：routing 动态性带来每步 CPU 重排 schedule（含 D2H 同步）与索引重建开销，小 M 时不可忽略；variant 组合爆炸（dtype×topk×layout×BN×arch）；SM 数硬编码换代要改。

**最有价值的经验**：依赖分解要先问"哪个维度上消费是独立的"；layer0 按 rank 排序把 tile 级依赖聚合成 rank 级 flag（信号数从 O(tiles) 降到 O(ranks)）；TBS 的"计数必须精确到每个 CTA"是最易写错的地方。

## 3. FlashOverlap（Infinigence，arXiv 2504.19519，EuroSys'26）

**定位**：不改 NCCL、几乎不改 GEMM 的轻量 tile 级重叠：GEMM epilogue 发 signal + 免费 reorder + counting kernel 卡住 NCCL。

**核心机制**：
- 因果链：想 tile 粒度触发→kernel 内要有信号；想不伤 GEMM→信号只放 epilogue（每 tile 只有 thread 0 做一次原子加）；想不重写通信→用原生 NCCL→要求连续地址→需要 reorder；想 reorder 免费→融进 epilogue 写出地址（pre）与下游 elementwise 的读入（post）。
- pre-reorder 不搬数据：让 GEMM 直接把 tile 写到"按 wave 排序后的连续位置"，通信段天然连续；post-reorder 融进下游 RMSNorm 的 gather 读。
- wave 归属靠实测不靠模型：开监控模式跑 10 次记录每个 tile 的全局完成序，10/10 次落同一 wave 窗口才算数；不一致就换 GEMM 配置（试 top-5/10），全部失败则放弃该 shape。
- wave_size = SM−2（1 个 SM 给 counting kernel、1 个给 NCCL）；分段方案小 shape 用穷举实测、大 shape 用解析模型（36 点带宽曲线插值 + GEMM 时长按让出 SM 的比例放大），预测误差 3.4%。
- counting kernel 是 1 block/1 thread 的自旋（CAS 匹配即清零），通信 stream 用高优先级，阻塞纯靠 stream 内顺序。

**关键数字**：最高 1.65×（4090 PCIe），平均 1.07~1.31×；A800 NVLink 收益小；naive"每 wave 一段"反而平均劣化 17.3%（在 50+ shape 中仅 4% 最优）——**分段大小必须调**；reorder 开销占 3.4~13.4%。

**适用边界**：M、N 必须整除 tile 尺寸（未做边界处理）；splitK/streamK 不能用（多 block 写一 tile 破坏信号语义）；wave 完成序不稳定的配置直接不可用；Hopper 未支持。

**最有价值的经验**："验证确定性而非假设确定性"；layout 变换永远藏进 producer 写出或 consumer 读入，绝不单独付钱；首段要小（尽早通信）、末段要小（尾部暴露最少）；预留 SM 的代价要显式进性能模型。

## 4. DeepEP（DeepSeek）

**定位**：EP/MoE dispatch+combine 的生产级 all-to-all 通信库，双路径设计（normal 高吞吐 / low-latency 低延迟），资源控制经验最丰富。

**核心机制**：
- normal 路径：NVLink+RDMA 两跳转发——token 经 IB 只发到目标节点**同 GPU-index** 的 rank，到达后由 forwarder warp 经 smem 扇出给节点内至多 8 个 GPU（匹配 IB ~50 GB/s vs NVLink ~160 GB/s 的 3.2× 带宽不对称）；所有缓冲是 head/tail 环形队列 + 滑动窗口乱序 release + min-head 懒回写。
- SM 组织：默认 20 个 SM，**每 2 个 SM 组成 1 个 channel**（共 10 channel），token 按 channel 静态切段；每 block 16 个 warp 精确分角色（internode dispatch：7 个 RDMA sender + 1 个 sender 协调 + 8 个转发/接收，奇偶 SM 分职；combine 为镜像）。
- QP 组织：每 channel 2 条 RC QP，数据与控制（head 回写）分离；low-latency 模式 QP 数必须等于本地 expert 数（per-expert QP 才能打满 NIC）。
- low-latency 路径：纯 RDMA（IBGDA），固定上界双缓冲，无 CPU 同步、兼容 CUDA graph；SEND/RECV 两 phase + recv hook 闭包，**传输期 0 SM 占用**——decode 双 micro-batch 交错的关键。
- handle 缓存：dispatch 返回全部路由元数据，backward/decode 复用可跳过 layout 计算与 CPU 同步。

**关键数字**：intranode 153~158 GB/s；internode EP32 约 58 GB/s；LL 模式 EP8 dispatch 77us；chunk 配置五元组按 EP 规模打表（如 EP64 dispatch =(32,288,8,128)）；V2 把训练 SM 从 24 降到 4~6。

**适用边界**：normal 路径 CPU 自旋等接收计数（不兼容 CUDA graph）；LL 双缓冲同时最多持 2 个结果；PCIe P2P 有内存序风险；FP8 要求 hidden 整除 128。

**最有价值的经验**：通信 SM 数应是一级参数且"打满带宽所需远比直觉少"；数据面与控制面分 QP/channel；多处"(x+channel+rank) mod N"轮转打散 incast 热点；超时+trap 兜底而不是无限自旋。

## 5. DeepSeek-V3 / DualPipe（arXiv 2412.19437 §3）

**定位**：系统级经验——大规模 MoE 训练中通信 kernel 与计算 kernel 长期共存时的资源纪律，以及 pipeline 级的通信隐藏。

**核心机制与经验**：
- 20/132 个 SM 足以同时打满 IB 和 NVLink，组织成 10 个 channel；其余 112 个 SM 全部给计算。
- warp specialization 分 IB 发送 / IB→NVLink 转发 / NVLink 接收三类角色，warp 数可按负载调整。
- 定制缓存控制指令（读写均不驻留 L1、限定 L2 提取粒度）+ 通信 chunk 自动调优，显著减少通信对计算 SM 的 L2 干扰——通信数据只过一遍，不应污染缓存。
- 每 token 限发至多 4 个节点（group-limited gating）使跨节点流量与选中 expert 数解耦。
- DualPipe：双向流水 + 把一个前向 chunk 与一个反向 chunk 配对，A 的 dispatch/combine 通信期恰好跑 B 的 attention/MLP，稳态下通信被完全隐藏；dW 延迟执行（zero-bubble）。

**最有价值的经验**：通信 kernel 若要与计算长期共存，必须 (a) SM 占用小且恒定 (b) 不污染 L2/DRAM (c) 接口纯异步；通信 SM 数的选择目标是"整体 pipeline 吞吐"而非"链路带宽最大化"。

## 6. TileLink / Triton-distributed（ByteDance，arXiv 2503.20313 / 2504.19442）

**定位**：tile-centric 编译抽象：通信 kernel 与计算 kernel 独立编写、独立调优，仅靠对称内存中的 tile 级信号耦合；Python 层写出接近手写 CUDA 的重叠算子。

**核心机制**：
- 核心抽象：tile_id 是唯一同步坐标 + 三映射——shape 映射（tile→数据切片）、rank 映射（tile→设备）、channel 映射（tile→信号槽位）。静态场景（TP）lower 成仿射公式，动态场景（MoE 路由）lower 成运行时查找表。
- 同步原语分三层且共用一套对称 signal buffer：设备端 tile 级 wait/notify（带 acquire/release 语义）、通信库段级"数据+信号"一体原语、host stream 级写值/等值——让 copy engine 和 SM 说同一种信号协议。
- wait 返回 token、用"消费 token"在 IR 里建假依赖，防止软件流水把异步 load 提前越过 wait——所有带流水的编译路径做细粒度同步都必须解决这个问题。
- 重叠时序完全由 threadblock swizzle 控制（rank 偏移 / node+local 二维偏移），不引入新调度器。
- producer 资源三形态显式可选：copy engine（0 SM）/ 少量 SM 的通信 kernel / 融合进 epilogue。SM 配额按带宽解析计算（如某跨节点 RS 例：116 SM 计算 + 1 SM P2P + 16 SM 一级归约）。
- 计数聚合通知：N 个 tile 各做一次 release 原子加，最后一个到达者发 notify——细粒度完成事件廉价聚合成粗粒度信号。

**关键数字**：~200 行 Python 达手写 Flux（~2000 行 CUDA）的 94.5%~130%；端到端平均 1.32×（dense 1.20×，MoE 1.54×）；all-to-all 在 ≤64 卡超过 DeepEP（128 卡因 IBRC 反被超）。

**最有价值的经验**：三映射 + swizzle + producer 形态 + 信号粒度——全部复杂性收敛到四个可替换组件；分布式 autotune 两个特殊点（每次 profiling 前重置信号、各 rank 全局同步选统一配置）。

## 7. ThunderKittens（HazyResearch）

**定位**：tile 为中心的 CUDA 模板框架：register/shared/global 三级 tile 类型 + warp/warpgroup/group 三级算子命名空间 + producer-consumer pipeline 骨架 + 多 GPU 原语（ParallelKittens）。

**核心机制**：
- 一切以 tile 坐标（单位是 tile 而非元素）表达；TMA 描述符 host 侧预生成。
- pipeline 模板：用户只填 producer 的 load/store 与 consumer 的 compute/finish，骨架管 smem 环形缓冲、mbarrier、相位位域；producer 主循环是事件驱动 poll——天然适合再挂一条通信流。
- 多 GPU：并行全局布局（同形张量在 N 卡的副本集合 + 可选 multicast 指针），远端显存当本地一样用 TMA 读写；multimem 在网归约；跨卡信号用 release 归约写 + relaxed 自旋读。
- 融合模式（GEMM+AllReduce 例）：同 kernel 内 SM 静态划分 compute/comm 角色；每个 C tile 一个跨卡 flag，算完即 signal、凑齐 N 卡即对该 tile 做在网归约——通信按 tile 流式启动。
- MoE dispatch 例：每收到一个 token 就对所属 128 行 tile 的计数器加一，GEMM loader 等计数凑满 128 才开始 load——token 到齐即开算。
- interpreter/VM 雏形：每 SM 一条指令流 + TMA 双缓冲预取指令——device 端调度的低配替代。

**最有价值的经验**：卡内同步用硬件 mbarrier、跨卡只用 relaxed 自旋 + release 归约的"精度分层"；signal 顺序与 wait 遍历顺序必须严格一致；flag 复位用独立小 kernel + 全卡 barrier 对齐退出；带超时 trap 的等待原语是调死锁的利器。

## 8. FlashDMoE（arXiv 2506.04667，NeurIPS'25）

**定位**：把分布式 MoE 整层（dispatch→expert FFN→combine）塞进单个 persistent kernel 的极限探索（基线一层要 261~432 个 kernel，它只要 1 个）。

**核心机制**：actor 模型——N−1 个 Processor block 干活 + 1 个 OS block（1 个调度 warp 集中派发任务 + 3 个订阅 warp 轮询到达信号并解码成任务描述符）；任务队列/就绪队列/门铃/中断标志全部是内存里的原子量；通信用单边 put+signal，对称缓冲按"轮次×双缓冲"静态错位防冲突（即隐式流控）。

**关键数字**：8×H100 上前向延迟最高降 6×、GPU 利用率 93%（基线 14~59%）、吞吐 5.7×；但 FP32-only、无 backward、6820 行手写 CUDA，多节点大 token 数会 buffer overflow。

**最有价值的经验**：persistent + 跨卡自旋是死锁温床（占用率必须全卡一致、信号序必须与等待序一致、flag 复用必须复位对齐）；静态预分配的隐式流控在规模变化时脆弱；集中式 device 调度器只有在通信模式高度不规则时才优于静态跨步领任务。

## 9. TokenWeave（MSR，arXiv 2505.11329）

**定位**：TP 推理的粗粒度（二分）token 切分 + wave 对齐 + multimem 融合通信。

**核心机制与数字**：token 只切 2 份且切分点对齐 wave 边界（H100 例：300 CTA 切成 132+168 保持总 wave 数 3，等分反而变 4 wave）；AllReduce 分解为 RS+AG 走 NVSwitch 在网归约，RMSNorm 在本 rank 1/N 分片上就地做（计算量÷N），融合 kernel 只占 **2~8 个 SM**（先前方案 16~20）；≥1024 tokens 才启用（以下回退），Llama-70B 8×H100 达 1.29×；MoE memory-bound 场景切半后权重仍要全读，收益差甚至为负。

**最有价值的经验**：每多切一块就多付一次 wave 量化损失和一次同步——粗二分+wave 对齐可能优于多路细分；通信后的 elementwise 应融进通信 kernel。

## 10. ISO（arXiv 2409.11155）

**定位**：sequence 维二分重叠的量化研究，价值在于把收益上限和干扰代价测清楚了。

**关键数字**：4090（PCIe）提升 35~48%，A800（NVLink）仅 0~15~25%；**NCCL 与 GEMM 并发使 GEMM 慢 15~20%**——通信抢 SM 的代价第一次被单独量化。attention 有 causal 依赖需保序，MLP 自由交错；decode 阶段可能负收益。

**最有价值的经验**：先测通信占比再决定投入——NVLink 机器上限只有 15~25%，干扰不控制会吃掉大半。

## 11. Syncopate / AutoOverlap（arXiv 2601.20595）

**定位**：编译器自动做单 kernel 内 chunk 粒度重叠（对 Triton kernel source-to-source 改写）。

**核心机制**：chunk = {连续数据范围, 对端 rank, 就绪信号} 三元组，把通信粒度与 kernel tile 结构、通信后端三者解耦；编译器插 per-tile wait/signal，并把 tile 执行顺序重排成**跟随 chunk 到达顺序** + chunk 内部再 swizzle 恢复 L2 局部性。平均 1.3×、峰值 4.7×（8×H100 + NVSHMEM）。

**最有价值的经验**："tile 执行序跟随数据到达序 + 块内 swizzle 补偿局部性"是 fused overlap kernel 的核心调度原则；这套改写可机械化，手写若干 pattern 后存在自动化空间。

## 12. CommFuse（arXiv 2604.24013）

**定位**：把 RS/AG 分解为 ring P2P 并与分块计算交错，贡献是**尾延迟消除的精确调度**。

**核心机制**：AG 侧第 i 步算 `(r−i) mod N` 号块（本地块最先）；RS 侧第 i 步算 `(r−i−1) mod N` 号块，且**把最终留在本 rank、无需发送的块排到最后一步**——最后一块算完没有暴露在外的通信。TP=4 MLP 例：122.3→77.1ms，通信隐藏 99.8%（常规分块只有 83.9%）。论文成熟度低（无硬件说明），数字仅作机制参考。

**最有价值的经验**：纯调度重排（零实现成本）就值约 8% 端到端——"无需通信的本地块最后算"应内置到任何 tile 调度器。

## 13. MSCCL++（Microsoft，arXiv 2504.09014）

**定位**：可编程 GPU 通信底座，为自定义 overlap kernel 提供 device 端 channel/semaphore 原语。

**核心机制**：三类 channel——MemoryChannel（GPU 线程直接读写远端映射内存，参与线程数由调用方定）、PortChannel（device 只往 FIFO 写一个 128-bit 触发器，host proxy 走 copy engine/IB RDMA，**0 SM**，单次 put ≤4GB、FIFO 深 512）、SwitchChannel（multimem 在网归约/多播封装，含 FP8）；semaphore 是**计数语义**（signal=远端 +1，wait=先取号再等"到达 ≥ 期望"），天然表达"等第 k 个 chunk"；signal 分 release 版（保证数据可见）与 relaxed 版（只同步执行流）；LL packet 把数据+flag 打包成 8/16B 原子单元，数据即信号（带宽减半换免同步往返）。

**关键数字**：collective 几何平均 1.7× vs NCCL（最高 5.4×）；推理端到端 1.2×。

**vs NVSHMEM**：不强制对称堆（任意 buffer 注册即可，与框架 allocator 共存容易）、计数 semaphore 结构化、0-SM PortChannel、原生 AMD；劣势是生态小、无 team/collective device 函数库、跨节点纯 GPU 发起不如 IBGDA 直接。**结论**：节点内 tile 级 overlap 用 MemoryChannel+SwitchChannel+计数 semaphore 几乎正好是需求清单；要走 Triton 编译路线则 NVSHMEM 生态更好；应抽象自己的 signal/wait 接口层使两者可替换。
