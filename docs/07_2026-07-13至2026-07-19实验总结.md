# 2026-07-13 至 2026-07-19 实验总结

## 1. 范围与结论摘要

本文汇总 2026-07-13（周一）至 2026-07-19（周日）的四卡 TP FP8 MoE 实验。
仓库中该时间窗内的有效实验记录集中在 7 月 15 日至 17 日，主要证据来自
`HANDOFF.md`、run manifest、两篇专项归档和对应提交正文。7 月 12 日形成的
FP8 `1708/2970µs` 收官结果仅作为本周起点，不计入本周新增实验。

本周的主线不是继续拆分 GEMM 与通信做多 stream overlap，而是在保持通算融合
框架的前提下，连续裁决三种通信组织：

1. **方案 A（通信 warp 化）判负**：把 peer TMA pull 放进 dense GEMM 所在 SM，
   会产生严重的 per-SM TMA 队列头阻塞；同 SM 共存比让渡专职通信 SM 更贵。
2. **P1（专职通信块内 per-lane 自由领取）小幅有效**：T=512 从 1709 降到
   1681µs，但没有减少所需通信 SM 数，证明 pull 的主要约束是 PCIe RTT 和
   在飞并发，而不是波同步本身。
3. **P2（源端 push + 收端本地 scatter）成为新默认**：T=512/T=1024 达到
   **1629/2777µs**，相对该轮记录采用的 serial FP8 2074/4030µs 耗时降低
   **21.5%/31.1%**。push 仅需 2 个 SM 即饱和，瓶颈从 PCIe wire 转移到
   收端本地 scatter。
4. **P2.5（warp 协作 scatter）尚未定案**：正确性门、端到端步骤和
   `comm_sms` sweep 被记录为通过，但具体性能 JSON/数值未入库；随后阶段归因
   `08p25` 引发整机 wedge，不能宣称性能收益。
5. wedge 事故推动形成四层死锁兜底：设备自旋有界、跨卡 mbarrier 有界、
   host fail-fast、故障注入验证。前三层已落码并完成静态审计；故障注入和
   GPU 上回归截至周末仍待执行。

### 2.3 报数和正确性口径

本周统一使用相对 baseline 的耗时降低：

```text
耗时降低 = (baseline_time - candidate_time) / baseline_time × 100%
```

正数表示候选更快，负数表示候选更慢。历史文档曾使用“加速比”，本文全部换算为
耗时降低。

FP8 correctness case 的相对误差约为 `4.27e-2~4.28e-2`。各实验与默认 FP8
路径处于同一误差水位，足以说明新增协议没有引入额外可见误差；但它仍高于旧的
元素级 `3.5e-2` 容差，根因候选包括 W1 的“反量化 → 交织 → 重量化”二次量化。
因此本文使用“协议正确性等价/同水位”，不把它表述为完整 FP8 正确性闭环。

T=1024 的历史 serial 锚点在不同文档中出现 4025 和 4030µs；P1/P2 的 run 记录
明确使用 4030µs，本文计算本周收益时沿用 4030µs，不混用不同轮次的基线。

## 3. 实验一：方案 A——把通信降到 GEMM producer warp

### 3.1 原理与假设

旧实现为 L0/L1 各保留 24 个专职通信 block。归因显示，L0 的主要暴露不是 wire
等待，而是通信 block 占用 SM 后导致 GEMM 少用 24 个 SM 的“让渡税”。

FP8 dispenser GEMM 每 block 有 9 个 warp，其中 warp 8 是 producer warp：
只有 lane 0 负责发本地 GEMM TMA，lane 1..31 基本闲置。方案 A 将通信任务塞入
这些闲置 lane，希望：

- 不增加线程数、寄存器上限和 GEMM 模板复杂度；
- 让 GEMM 使用全部 SM；
- 用 SM120 independent thread scheduling 使 lane 0 的 GEMM producer 与
  其余 lane 的通信并发推进；
- 回收 L0 约 264µs、L1 约 142µs 的 SM 让渡税。

L0 用 lane 1..4 各维护一个 in-flight token；L1 用 31 个 lane 在 GEMM 运行期间
推送已完成 job，并让 consumer warps 在 GEMM 后协助排空。完整设计见
[`2026-07-16_方案A_通信warp化设计与落地.md`](归档/2026-07-16_方案A_通信warp化设计与落地.md)。

### 3.2 首轮结果

`tp_run_20260716_063155`，卡组 0-3：

| 档位 | median (µs) | min (µs) | 相对对照 |
|---|---:|---:|---|
| 默认 FP8 | 1709 | 1703 | — |
| L0 warp | **3443** | 1745 | median 慢 101%；min 慢 2.1% |
| L1 warp | 1897 | 1883 | 慢 11.0% |
| L0+L1 warp | 1930 | 1910 | 慢 12.9% |
| L0+L1 warp，T=1024 | 3434 | 3412 | 对照 2932，慢 17.1% |

正确性 `rel_err=4.27e-2`，与默认 FP8 路径同水位。L0 单开出现进程级双稳：
多数迭代约 3.4ms，少数迭代约 1.75ms；但 L0+L1 双开时同一个 L0 kernel
处于稳定快态。卡 0-3 满频、4-7 空闲，未观察到外部 GPU 负载解释该现象。

### 3.3 三分解探针与根因裁决

为区分“producer warp 发射饥饿”和“同 SM TMA 队列争用”，新增
`tools/diag_warp.py` 和 gate/slot 可控的探针 kernel，将融合耗时拆为：

1. 满 SM 的纯 GEMM 上限；
2. 加 peer pull 后的共存税；
3. 再加 GEMM gate 后的 straggler 税。

`tp_run_20260716_070406`，30 次迭代全程稳定：

| 探针档位 | median (µs) | 解释 |
|---|---:|---|
| 纯 FP8 GEMM | 752 | 跨口径参考 |
| L0 warp 几何、无 pull | 742 | warp 几何本身免费 |
| L0 warp + pull、无 gate | 968 | **共存税 +226** |
| L0 warp 完整融合，4 lane/SM | 964 | gate/straggler 税约 −4≈0 |
| L0 warp，2/1 lane/SM | 947/917 | 1 lane/SM 仍有 +175 共存税 |
| 默认 L0 融合 | 935 | 融合税 +183 |
| L1 纯 GEMM / warp 融合 / 默认融合 | 383/729/556 | warp 融合税 +301，默认 +173 |

结果排除了“发射饥饿 → straggler → gate 车队”假设，坐实了
**per-SM TMA 队列 head-of-line blocking**：µs 级 peer TMA read 与本地
GEMM A/B tile load 共用同一 SM 的 TMA 队列，慢 peer read 阻塞 GEMM 流水。
共存税随 comm lane 数单调，且 1 lane/SM 仍高达 175µs。

默认方案也使用 peer TMA，但通信和 GEMM 位于不同 SM，因此不会拖慢 GEMM。
由此得到本机平台结论：**把 peer TMA pull 塞进 dense GEMM 所在 SM，比让渡
专职通信 SM 更贵**。

### 3.4 裁决

- L1 warp 判负，默认关闭；推流人手减少和 prered 串行化让排空尾巴增长，超过
  满 SM GEMM 的收益。
- L0 warp 现形态判负，默认关闭；964µs 仍慢于默认 935µs。
- 唯一可能翻盘的变体是用普通 `ld.global` 向量加载代替 peer TMA，绕开 TMA
  队列，但可能转而争用 LSU/MSHR，本周未立项验证。
- 这次负结果说明 intra-SM overlap 只有在通信模式与计算 tile 流自然对齐时才
  合适；L0 的 token gather/scatter 和 L1 的跨行块 prered 都不满足此前提。

## 4. 实验二：P1——专职通信 block 内 per-lane 自由领取

### 4.1 原理与假设

方案 A 证明 per-lane 组织本身可行，但放错了资源位置。P1 保留“专职通信 SM +
完成后转岗 GEMM”的 inter-SM 几何，只把原来的波同步拉取改为 per-lane 独立拉取：

- 旧路径每波 20 个 lane 一起发 peer pull，并在 block barrier 等最慢 RTT；
- 新路径每个槽线程独立 `atomicAdd` 领取全局 `pull_order`，使用私有
  smem/semaphore，不做块内波同步；
- 慢 RTT 只拖慢自己的 lane，不再把同波其他请求一起卡住；
- 20 条自由循环按 stride-8 分散到 5 个 warp，避免挤在一个 warp 内串行发射。

原假设是 24 个通信 SM 主要在补偿波同步低效，per-lane 化后可把拐点压到
8~12 SM。

### 4.2 结果与裁决

`tp_run_20260716_073019`：

| 档位 | median (µs) | 结论 |
|---|---:|---|
| 波同步 @24 | 1709 | 对照 |
| lane @24 | **1681** | 快 28µs，耗时降低 1.6% |
| lane @16/@12/@8/@4 | 1775/1808/1904/2633 | 16 SM 已开始回升 |
| 波同步 @4 | 3814 | lane@4 快 1181µs |
| lane，T=1024 | **2831** | 对照 2935，快 104µs，降低 3.5% |

正确性 `rel_err=4.27e-2`，与默认路径同水位。lane 在所有 `comm_sms` 档位都
优于波同步，说明组织优化有效；但性能拐点仍在 24 SM，核心假设被证伪。

原因是 PCIe pull 属于高 RTT 弱路径：每条 4KB FP8 token 行并未打满带宽，
需要约 `24 block × 20 slot = 480` 个在飞请求隐藏往返延迟。24 SM 是真实并发
需求，不只是波同步低效的补偿。P1 因小幅收益一度成为默认，但数据门控立即触发
P2：若要减少通信 SM 数，必须从 pull 切换到无 RTT 往返的 posted write。

本阶段最好结果相对 serial FP8 2074/4030µs 的耗时降低为 18.9%/29.8%。

## 5. 实验三：P2——源端 posted write，收端本地 scatter

### 5.1 原理

P2 将 L0 数据移动方向从 pull 改为 push：

```text
源 rank 本地 FP8 token
  → posted write 到各目标 rank 的 staging plane
  → system fence
  → release 写 per-token seq flag
  → 目标 rank acquire 等 flag
  → 从本地 staging scatter 到 8 个 expert slot
  → 行块计数到达后放行 GEMM
```

关键点如下：

- 每个源 rank 只写目标 rank staging 中属于自己的 plane，保持单写者；
- `push_order` 与目标消费顺序一致；
- seq 单调递增，无需每轮清零 flag；
- 收端等待 flag 后只读本地 HBM，移除 peer-read RTT；
- 跨迭代覆盖由双 `pcie_device_barrier` 保护；
- 依赖链为 `GEMM ← scatter ← flag ← peer push`，push 只依赖源端本地量化
  数据，跨 rank 依赖无环。

微基准显示 posted write 强路径约 50.9GB/s，少量 SM 即可打满，因此预计可把
24 个通信 SM 拆成少量 push SM 加少量本地 scatter SM。

### 5.2 结果

`tp_run_20260716_075314`：

| 档位 | median (µs) | 结论 |
|---|---:|---|
| push @24，push_sms=4 | **1629** | 比 lane 1682 快 53µs |
| push，T=1024 | **2777** | 比 lane 2830 快 53µs |
| comm_sms=6/8/10/12/16 | 2513/1875/1752/1749/1731 | 拐点仍未左移 |
| comm_sms=8，push_sms=2/4/6 | 1750/1875/2518 | **2 个 push SM 已饱和** |

正确性 `rel_err=4.28e-2`，与默认路径同水位。P2 相对本周起点 1709/2935µs
分别快 80/158µs；相对该 run 记录采用的 serial FP8 2074/4030µs，耗时降低
**21.5%/31.1%**。`TK_L0_PUSH=1` 因此翻为默认，稳定推荐点仍是
`comm_sms=24, push_sms=4`；`push_sms=2` 只在 `comm_sms=8` 档验证过，不能
直接宣称全局最优。

### 5.3 瓶颈转移

虽然 wire 已退出关键路径，最佳 `comm_sms` 仍是 24。根因已经从 PCIe RTT
变为收端本地 scatter 的组织效率：

- 每个 lane 串行处理一个 token；
- 每 token 需要 8 次 TMA store；
- 随后执行一次 `store_async_wait`；
- 单 lane 周期约 10µs；
- scatter SM 从 4 增到 20 可回收约 246µs，和实测 sweep 一致。

这是好消息：通信方向已经正确，剩余问题是本地 HBM 搬运的并行化，不再是难以
消除的跨卡往返延迟。

## 6. 实验四：P2.5——warp 协作式本地 scatter

### 6.1 原理

P2.5 将“每 lane 串行搬一个 token”改为“每 warp 协作搬一个 token”：

- 9 个 warp 独立领取 `pull_order` 中的 token；
- lane 0 acquire 等待到达 flag；
- 32 个 lane 每人搬运 128B 段，并行写入 8 个 expert slot；
- 数据路径改为纯 LSU 向量读写，不使用 scatter TMA、mbarrier 和
  per-token `store_async_wait`；
- 全员 `threadfence` 后同步，由 lane 0..7 分别发布 8 个 slot 的行块计数。

目标是让 scatter 吞吐提升数倍，把 `comm_sms` 拐点压到 8~12，预计端到端
可达 1530~1580µs。

### 6.2 实测状态

`tp_run_20260716_081949` 的 `03p25` 正确性门、`04p25` 端到端步骤和
`05p25` 的 `comm_sms={4,6,8,12,16,24}` sweep 均被记录为通过，但仓库没有
保存本轮具体 JSON、summary 全文或各档 latency，因而不能判断：

- 是否优于 P2 的 1629/2777µs；
- 最优 `comm_sms` 是否真的左移；
- 预期的 50~100µs 收益是否兑现。

随后 `08p25_time_stages_scatwarp` 阶段归因步骤发生整机 wedge。卡住 worker
的内核栈位于 setup 阶段的 `uvm_map_external_allocation`，更像排队在 RM GPU
组锁后的受害者；元凶可能是前一步 teardown 残留，也可能是 08p25 worker 集合中
先发故障。由于缺少 summary 尾部和复现实验，根因截至周末没有闭环。

因此 `TK_L0_SCAT_WARP` 保持默认关闭；P2.5 的正式结论是：
**功能步骤有通过记录，性能和稳定性均未定案。**

## 7. wedge 事故与死锁兜底实验

### 7.1 事故机理

本周出现两次相关 wedge：P2.5 首测和后续 08p25。已观察到的事故链为：

```text
协议 bug 或某 rank 先退出
  → 其他 rank 的 persistent kernel 在跨卡 flag/mbarrier 上无界等待
  → 超时 kill 无法抢占 kernel，进程进入 D 态
  → context 销毁、IPC unmap 或 NCCL teardown 卡在 RM/uvm 路径
  → nvidia-smi 和新 CUDA 进程全部排队
  → 整机只能重启
```

RM GPU 组锁影响全机，即使实验只用了 0-3 卡，也可能让 8 张卡全部不可用。

### 7.2 四层兜底

本周完成了前三层实现和静态审计，并加入第四层动态验证工具：

| 层次 | 实现 | 作用 |
|---|---|---|
| 设备自旋 | `PCIE_SPIN_GUARD_DECL/TICK` | 约 32s 超时执行 `trap`，杀整个 kernel |
| 跨卡 mbarrier | `pcie_sync::guarded_wait` | `try_wait + clock64`，约 40s 超时 trap |
| host 异常路径 | `distributed._fail_fast_exit` | traceback 后 `os._exit(1)`，跳过 synchronize/NCCL destroy/IPC unmap |
| 故障注入 | `tools/fault_inject_kill_rank.py` | SIGKILL 一个 rank 后检查其余进程退出、nvidia-smi 存活和 GPU context 可复用 |

设备侧审计覆盖全部跨卡/跨块自旋、`tk_moe.cu` 14 处跨卡数据喂入的 semaphore
等待及 tileoverlap dispatch 等待。本地 GEMM 流水 mbarrier 保留裸 wait，
因为生产者和消费者位于同一 kernel，且任何跨卡 gate trap 会连带终止整个 kernel。

截至周末，故障注入尚未在 GPU 机上跑通，guard 后的 1629/2777µs 性能回归也未执行。
因此当前能声称的是“所有已知设备等待点已静态有界化”，不能声称“已经动态证明
整机永不再 wedge”。详细边界见
[`06_死锁兜底体系.md`](06_死锁兜底体系.md)。

## 8. 一周性能演进

| 阶段 | T=512 (µs) | T=1024 (µs) | 相对 serial 2074/4030 的耗时降低 | 状态 |
|---|---:|---:|---:|---|
| 本周起点：默认 FP8 pull | 1709 | 2935 | 17.6% / 27.2% | 对照 |
| 方案 A：同 SM 通信 warp | 1930（双开） | 3434 | 6.9% / 14.8% | 判负 |
| P1：专职块 per-lane pull | 1681 | 2831 | 18.9% / 29.8% | 有效，后被 P2 替代 |
| P2：posted write + 本地 scatter | **1629** | **2777** | **21.5% / 31.1%** | 当前默认/最好 |
| P2.5：warp scatter | 数值未入库 | 数值未入库 | 不可计算 | 未定案 |

从 P1 到 P2，T=512 再降低 3.2%，T=1024 再降低 1.9%；从本周起点到 P2，
分别降低 4.7% 和 5.4%。更重要的不是单次 53µs，而是瓶颈性质发生改变：

```text
专职 block 波同步效率
  → peer pull RTT / 在飞并发
  → posted write 后的本地 scatter 吞吐
```

前两项受 PCIe 弱路径约束较强，最后一项是可继续优化的本地数据搬运问题。

## 9. 本周形成的可复用认识

1. **不要只看“占了多少 SM”判断 overlap 是否划算。** 同 SM 放置通信可能释放
   SM 数，却引入发射槽、TMA 队列、LSU/MSHR 等更隐蔽且更贵的资源竞争。
2. **通信方向比数据字节数更关键。** FP8 把 token 行从 8KB 减到 4KB，并没有
   降低 pull 所需 SM，因为瓶颈是 RTT；改成 posted write 才真正移除往返依赖。
3. **per-lane 自由化能消除波内长尾，但不能创造带宽或降低 RTT。**
   P1 全档优于波同步，却无法把 24 SM 拐点左移。
4. **必须用分解探针裁决机制。** “纯 GEMM → 加通信无 gate → 完整融合”的阶梯
   直接将 226µs 共存税与约 0µs gate 税分开，避免围绕错误假设继续调参。
5. **正确性同水位不等于精度口径闭环。** 新协议没有额外误差，但 FP8 二次量化
   仍使整体 rel_err 超旧容差，性能结论和最终正确性结论必须分开。
6. **persistent kernel 的失败模式必须先设计。** 新协议首测要单步隔离；每个
   跨卡 flag、watermark、计数器和 mbarrier 都必须回答生产者是谁、何时永不到达，
   并提供有界 trap。
7. **结果资产要与结论一起持久化。** P2.5 只有“步骤通过”的文字记录、没有具体
   JSON，导致后续无法恢复性能结论；新 run 必须保存 manifest、summary、logs 和 JSON。

## 10. 下周建议

按风险和依赖顺序：

1. 在空闲卡组上单步编译并跑 `03p25`，确认 guard/guarded_wait 改动不影响正确性；
2. 单独复跑 `08p25`，让潜在协议死锁以 trap/FAIL 形式暴露，收集完整 summary、
   log 尾部和 dmesg/Xid；
3. 跑 P2 的 04 档回归，确认死锁兜底没有让 1629/2777µs 回退；
4. 单独执行故障注入，验证 kill 一个 rank 后其余进程有界退出、`nvidia-smi`
   存活且四卡可重新创建 context；
5. 只有上述安全门通过后，才重跑 P2.5 的 04/05/08 矩阵并保存完整结果；
6. 最后按 warmup=20 的唯一主配置做全量回归，生成可对外引用的最终数字。
