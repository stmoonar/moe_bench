# 背景知识

## 1. MoE 层与分布式执行

### 1.1 MoE 层结构

一个 MoE（Mixture-of-Experts）层 = 路由器（gate）+ E 个专家（每个专家是一个两层 FFN）：

1. **Gate/路由**：每个 token 计算 gate 分数，选出 top-k 个专家，并得到 k 个归一化权重（softmax）。
2. **layer0（up projection）**：token 被送到它选中的每个专家，各做一次 `x @ W1^T`。常见变体是 gate/up 双投影（SwiGLU）：`W1` 输出 2×intermediate 维，前半为 gate、后半为 up，激活为 `silu(gate) * up`。
3. **layer1（down projection）**：激活结果做 `h @ W2^T` 回到 hidden 维。
4. **combine**：同一 token 的 k 份专家输出，按 gate 权重加权求和，得到该 token 的最终输出。

符号约定：

| 符号 | 含义 |
|---|---|
| `E` | 专家总数 |
| `topk` | 每 token 路由的专家数 |
| `ntokens` | 全局 token 数（所有 rank 之和） |
| `M = ntokens * topk` | token-assignment 总数（每个 token 复制 topk 份） |
| `N` / `K` | GEMM 输出/输入维（layer0: N=ffn_hidden, K=hidden；layer1: N=hidden, K=ffn_hidden） |
| `TP` / `EP` | 张量并行度 / 专家并行度，`world_size = TP x EP` |

### 1.2 EP 与 TP 两种切分

- **EP（Expert Parallelism）**：专家整份分布在不同 GPU（每卡 `E/EP` 个专家）。token 必须被**发送**到目标专家所在的卡（dispatch），算完再**送回**（combine）。通信本质是 All-to-All。
- **TP（Tensor Parallelism）**：每卡持有**所有**专家权重的一个切片（ffn_hidden 维切分）。每卡对全量 token 算部分和，最后跨卡规约。
- 二者可组合：`world_size = TP x EP`，同一 EP 组内的 TP 个 rank 切分 ffn_hidden 维。

### 1.3 通信为什么是瓶颈

在序列并行布局下，每个 rank 起初只持有 `ntokens/world_size` 个 token 的分片。一个 MoE 层的完整数据流是：

```
AllGather(token 分片) → scatter(按 expert 重排) → GroupGEMM0 → 激活
  → GroupGEMM1 → gather(还原 token 顺序) → topk 加权求和 → ReduceScatter
```

实测（论文数据，8×H800 + Megatron-LM）：dispatch/combine 通信占 MoE 端到端时间约 **47%**。这就是要隐藏的对象。

### 1.4 粗粒度重叠为什么不够

传统做法（Tutel、FasterMoE 等）：把 token 沿 M 切成几个大 chunk，通信 kernel 和计算 kernel 放不同 stream 流水。四个根本缺陷：

1. **GEMM 切小掉效率**：chunk 变小 → 单个 GEMM 打不满 SM → 分段计算总时间 > 不分段。
2. **首尾气泡**：流水第一段通信、最后一段通信没有计算可重叠，必然暴露。
3. **时机不可控**：独立 kernel + 多 stream，GPU 编程模型无法精确控制重叠时机。
4. **CPU 调度开销**：kernel 数量多，M 小或 E/topk 大时 host 调度时间甚至主导。

**通算融合的答案**：把依赖分解到 **tile 粒度**（GEMM 本来就按 tile 组织，不破坏计算效率），用 **kernel 内的信号机制**（而非 stream/event）表达依赖，用 **SM 级的线程块分工**隔离通信对计算的干扰。

## 2. GPU 执行模型相关事实

### 2.1 SM、threadblock、延迟隐藏

- GPU 由几十~一百多个 SM 组成（A100=108，H100=132，sm120 需实测查询）。
- kernel 以 threadblock（CTA）为调度单位分派到 SM。**Ampere 风格的 GEMM kernel 通常发射远多于 SM 数的 threadblock**，每个 SM 驻留多个 block，某个 block 因访存/自旋等待停顿时，SM 的 warp 调度器切到其他 block —— 这是"细粒度 I/O 塞进 kernel 而不拖垮计算"在 Ampere 上成立的根本原因。
- Hopper 的高效 GEMM 改用 **persistent warp-specialized** 形态：每 SM 只驻留 1 个 block，block 内 producer warp（搬数）与 consumer warp（MMA）流水。这种形态下往流水里插长延迟远端 I/O 会直接拉长关键路径 —— 所以 Hopper 上通信必须**隔离到专门的 block**。
- **sm120 迁移应参考 Ampere 形态**（非持久、多 block/SM、cp.async + mma.sync）。

### 2.2 stream、event 与 kernel 并发

- 不同 stream 上的 kernel 可以**并发驻留**在同一 GPU 的不同 SM 上（硬件调度）。layer1 的"水平融合"就是：主 stream 跑 GEMM（少用几个 SM），高优先级 stream 跑一个只占少量 CTA 的通信 kernel，两者物理并行。
- `cudaEventRecord` / `cudaStreamWaitEvent` 只用于**编排边界**（如"通信 kernel 必须等 barrier 缓冲清零之后再启动"）；**tile 级依赖不用 event，用显存里的 flag**。
- 高优先级 stream（`cudaStreamCreateWithPriority`）保证通信 kernel 的 CTA 优先拿到 SM。

### 2.3 跨 GPU 通信原语（单机）

从上到下按抽象层次：

1. **NCCL 集合通信**：粗粒度、host 发起、整 tensor。通算融合**不用它搬数据**（只把 torch.distributed 进程组用于控制面：交换 handle、广播 UID、barrier）。
2. **`cudaMemcpyAsync` P2P DMA**：当两卡间开启 P2P 后，`cudaMemcpyAsync(dst_peer_ptr, src_ptr, ..., cudaMemcpyDefault, stream)` 由 copy engine 走 NVLink/PCIe 直接搬运，不占 SM。搭配 CUDA stream memory ops（`cuStreamWriteValue32`/`cuStreamWaitValue32`）可以在 stream 上按序"点灯/等灯"，实现纯 DMA 的带信号流水。
3. **SM 直接远端访存**：kernel 里把**对端 GPU 的显存指针**当普通指针 `ld/st`。前提是该指针可被本卡解引用——两种获得方式：
   - **CUDA IPC**：对端 `cudaMalloc` 后 `cudaIpcGetMemHandle`，经 CPU 侧交换 handle，本卡 `cudaIpcOpenMemHandle(..., cudaIpcMemLazyEnablePeerAccess)` 得到映射指针（P2P 在打开 handle 时懒启用）。
   - **NVSHMEM**：PGAS（分区全局地址空间）库，`nvshmem_ptr(ptr, peer)` 返回可直接解引用的对端指针。
4. **system-scope 原子/内存序**：跨 GPU 的 flag 同步必须用 `.sys` scope——`st.release.sys` / `ld.acquire.sys` / `red.release.sys`（或 CUDA C++ 的 `cuda::atomic_ref<T, cuda::thread_scope_system>`）。同 GPU 内用 `.dev`（device scope）即可。**注意**：PCIe 上 `cudaDevP2PAttrNativeAtomicSupported` 通常为 false —— 跨卡 RMW 原子不可用，必须退化为纯 store/load 的握手（ring-token 模式）。

### 2.4 flag/信号（"红绿灯"）模式

通算融合全部 tile 级依赖都用这个模式表达：

- **生产者**：把一段数据写到消费者可见的缓冲后，向一个约定位置的 int32 flag 写 1（保证"数据先到、灯后亮"：DMA 路径靠 stream 顺序 + `cuStreamWriteValue`；kernel 路径靠 `fence` + release store）。
- **消费者**：threadblock 在使用该段数据前，自旋轮询 flag（acquire load）直到为 1。
- flag 数组本身放在对称缓冲或本地显存（谁轮询就放谁本地——**让轮询方读本地、点灯方写远端**，这是 PCIe 友好的方向）。

### 2.5 NVSHMEM 与对称内存

- NVSHMEM 是 PGAS 库：每个 PE（GPU 进程）在**对称堆**上分配相同大小的缓冲，`nvshmem_ptr(ptr, peer)` 返回可直接解引用的对端指针（单机 P2P 可达时），还提供 kernel 内的 `put/get/signal` 细粒度 API。
- **bootstrap 不需要 MPI**：可用 UID 模式——rank0 `nvshmemx_get_uniqueid`，经 torch.distributed 广播给所有 rank，各自 `nvshmemx_init_attr(NVSHMEMX_INIT_WITH_UNIQUEID, ...)`。
- 单机场景 NVSHMEM 与 CUDA IPC 二者可互换。**在消费级 Blackwell + 纯 PCIe 上 NVSHMEM 是否可用需要实测验证**——备选方案是 cudaIPC + 自研 barrier。

### 2.6 copy engine vs SM copy

- copy engine（DMA）：`cudaMemcpyAsync`，不占 SM，适合大段连续拷贝；每卡有数个独立引擎，可与计算完全并行。
- SM copy kernel：向量化 `ld/st`（如 128-bit `uint4`），占 SM，但能做"边搬边算/边搬边点灯"的融合逻辑。
- AllGather 对 bf16/fp16 默认走 **DMA 路径**；SM copy 是备选。

## 3. 路由元数据（所有 MoE 融合算子的输入契约）

MoE 融合算子不做 gate 本身，但消费 gate 的产物。以下数据结构是理解实现原理的前提：

| 名称 | 形状/类型 | 含义 |
|---|---|---|
| `splits` | `[E]` int32 | 每个专家分到的行数（token-assignment 数），Σ = M |
| `scatter_index` | `[ntokens, topk]` int32 | "(token t, 第 k 选择) 这条 assignment"在**按 expert 排序后的缓冲**中的目标行号 |
| `gather_index` | `[M]` int32 | scatter_index 的逆映射：排序后第 j 行 ← 全量输入的第几行（token 行号） |
| `output_vec_scale` | `[M_this_ep]` float32 | 逐 assignment 行的 gate 权重（combine 的加权系数） |

生成方式（纯 torch 即可）：`flat = topk_ids.view(-1)`（长度 M）→ 稳定 argsort 得 expert 排序 → `scatter_flat[order[j]] = j` → `splits = bincount(flat, E)`。EP 时每个 rank 只负责专家区间 `[ep_start, ep_start + E/EP)`，对应排序缓冲里一段**连续**行 `[m_start, m_start + M_this_ep)`。

**关键点**：`splits` 需要一份 CPU 拷贝——输出张量形状（`M_this_ep`）与 workspace 大小由 host 决定、grouped GEMM 的 launch 配置也在 host，所以路由结果必须至少有一个标量（或 splits 全量）回到 host。这是整条流水里唯一的强制 device→host 同步点。

## 4. 术语表

| 术语 | 定义 |
|---|---|
| tile | GEMM 输出矩阵的 `BLK_M×BLK_N` 分块，threadblock 的工作单位，细粒度重叠的对齐粒度 |
| shared tensor | 连接生产者算子（通信/计算）与消费者算子的共享缓冲，依赖分析的对象 |
| dispatch / combine | MoE 的两次 token 通信：发往专家 / 收回并按 topk 加权求和 |
| grouped GEMM | 一次 kernel 算完 E 个变长 GEMM problem |
| ProblemVisitor / tile scheduler | grouped GEMM 内把 (problem, tile) 分派给 threadblock 的调度器 |
| gather_A / scatter_D | A 读、D 写的行级间接寻址（查 index 表） |
| 红绿灯 / arrival flag | 显存里的 int32 信号：生产者置 1，消费者 acquire 自旋等待 |
| 对称内存 | 各 rank 等大的、互相可见的缓冲（NVSHMEM 对称堆或 cudaIPC 映射） |
| 垂直/水平融合 | 通信塞进计算 kernel 的头尾 vs 通信专职 CTA 与计算 CTA 并列 |
| n_p / n_c | 计算/通信线程块数量划分（自适应负载分配的调节对象） |
| push / pull（write/read 模式） | 数据流动靠"远端写"还是"远端读"。**PCIe 上远端读极慢，必须 push** |
| ring reduce-scatter | 环形规约：world_size 步，每步处理一个 rank 的 token 段并传给邻居 |
| system scope（`.sys`） | 跨 GPU 可见的原子/内存序 scope；同卡内用 `.dev` |
| sm_margin | GEMM 主动少用的 SM 数（给通信 CTA 留位置） |
