# 测试与调试指南

## 1. 强制默认口径

- Python：`/root/miniconda3/envs/vllm-td/bin/python`。
- 工作目录：`/workspace`，不能在 `moe_bench/` 内运行 `python -m moe_bench...`。
- 配置：`moe_bench/configs/tp_rtx_pro5000_4gpu_fp8.yaml`，通用 benchmark 必须显式传入。
- 卡组优先级：`0,1,2,3`，其次 `4,5,6,7`。
- 每次测试前先用 `nvidia-smi` 检查利用率、显存和现有进程；卡不空闲就换组或停止测试。

通用入口示例：

```bash
cd /workspace
CUDA_VISIBLE_DEVICES=0,1,2,3 \
  /root/miniconda3/envs/vllm-td/bin/python -m moe_bench.bench \
  --config moe_bench/configs/tp_rtx_pro5000_4gpu_fp8.yaml
```

正式配置为 H=4096、I=3072、E=64、TopK=8、TP=4、FP8、512 token/rank、warmup=20、
bench=50、balanced routing、正确性开启。A/B 只能覆盖待裁决字段，所有覆盖必须进入
结果目录、`HANDOFF.md` 和提交信息。

## 2. 推荐执行顺序

1. `git status` 与 commit 记录；确认代码、配置和远端环境一致。
2. `nvidia-smi` 选择空闲卡组。
3. 首次或大改后先运行 CPU/静态 builder 校验和语法编译。
4. `QUICK=1 bash moe_bench/tools/run_tp_all.sh` 做短回路。
5. 正确性、schedule、协议裁决全部通过后再跑完整 `bash moe_bench/tools/run_tp_all.sh`。
6. 汇总 JSON、结果目录、环境信息和异常；更新主题文档与 `HANDOFF.md`。

`tools/run_tp_all.sh` 的每一步都各自起一次独立的分布式 worker（预检 → 编译 →
GEMM 裁决 → 正确性对拍 → 性能 → 分阶段归因 → sweep），单步超时或失败不会中断后续
步骤，失败详情记在 `logs/<step>.log` 和 `summary.txt`。可覆盖的环境变量只有
`PYTHON_BIN`/`VENV`/`CARDS`/`QUICK`/`STEPS`：`QUICK=1` 跳过 sweep 步骤，只跑核心
流程；`STEPS='01_|03_|04_'` 这类正则可以只跑匹配的步骤名，用于怀疑某一步或需要
定位死锁时的单步隔离重跑。

## 3. 验证分层

| 层级 | 必查内容 | 典型工具 |
|---|---|---|
| Host 调度 | 表形状、计数闭合、host/GPU 逐元素一致、balanced+skewed、端到端数据流模拟 | `tools/preflight_tp_cpu.py`（无 GPU 依赖） |
| 单 kernel | FP8 GEMM/量化、行映射、scale、padding | 隔离入口与 torch/reference 对拍 |
| 协议 | 数据逐字节、signal 与 expected 双向对账、30 轮偶发竞争 | 历史专用 `validate_*.py` 工具已随 slim 分支移除；当前由 `preflight_tp_cpu.py`（host/GPU 表对账）+ 全链路 verify 覆盖，逐字节级对账需检出 `fp8_tp` 分支复现 |
| 全链路正确性 | `tktp` vs reference/serial，所有 rank、目标 shape | `tools/run_tktp.py` / benchmark verify |
| 分段性能 | fused vs. gemm_alone 对照，rank max，性能账闭合 | `tools/time_tp_stages.py` |
| 全矩阵 | FP8 主口径、T/NE 档位、comm/push SM sweep、重复跑 | `tools/run_tp_all.sh` |
| baseline 调优 | serial 侧 triton tile config 扫描（单卡，320 候选，带正确性门） | `tools/tune_triton_moe.py`，机制见 [08 §6](08_NCU单kernel计算效率_gg8_vs_triton.md) |

协议改动不能只靠一次端到端输出“看起来对”。至少要把数据面和完成信号拆开，对 expected 表做
源汇双向对账，并用多轮 stress 抓内存序偶发错误。

## 4. 性能报数纪律

- schedule、量化、routing gather 等每步真实成本都计入 `run()`。
- 每轮同时保存 serial 与 tktp；注明 serial 是否使用调优配置。**截至 2026-07-26
  历史全部轮次都是"否"**——本机没有 vLLM 内置 config，serial 一直跑兜底默认
  tile。用 `tools/tune_triton_moe.py` 调优后须经 `VLLM_TUNED_CONFIG_FOLDER`
  显式挂载，并把该目录路径记进结果目录和 `HANDOFF.md`（口径见
  [08 §6](08_NCU单kernel计算效率_gg8_vs_triton.md)）。
- 多 rank 计时取 rank max，再报告预先约定的统计量；不能用孤立 min 掩盖稳定 med。
- 发现双峰时先复跑 serial、记录 clock/利用率和 GPU 进程，确认是否为共享环境干扰。
- 当前主配置默认 warmup=20、bench=50。历史 warmup=5 或额外 T=1024 的数字只作参考。
- 任何 shape、precision、token、warmup/iters、正确性或 `TK_*` 覆盖都必须显式记录。

## 5. 常见故障定位

| 现象 | 优先检查 |
|---|---|
| `ModuleNotFoundError` | 是否误在 `/workspace/moe_bench` 内运行；应回 `/workspace` |
| setup 设备混用/极慢 | host tensor 是否漏写 `device="cpu"` |
| `illegal instruction` | named barrier 是否复用、arrival count 是否混用 |
| persistent kernel 超时 | 是否占满 SM 并等待一个需要辅助 kernel/CE 才能产生的 flag |
| 改 C++ 但行为没变 | 是否改了构建副本而非 `kernels/tileoverlap/common` 正本；缓存 key 是否变化 |
| 切 world/RB 后 shape 异常 | 是否错误复用了旧 `.so`，需要 clean 或检查 build cache key |
| FP8 正确性略超旧容差 | 区分 serial 自身 FP8 误差与 W1 二次量化；查看 rel_err 和超差比例 |
| suite 失败难定位 | 用 `STEPS` 过滤到失败步骤单独重跑，配合 `logs/<step>.log` 定位 |

更深入的 profiler 流程示例见
[08_NCU单kernel计算效率_gg8_vs_triton.md](08_NCU单kernel计算效率_gg8_vs_triton.md)
（单卡 NCU 锁频对比的具体命令、口径与坑）。SM120 上优先使用 CUDA Event、torch trace、
nsys 和 NCU；TK 原生 `TKProfiler` 当前只在 SM100/103 路径编译，不能直接在本项目删除
架构宏强开。更完整的历史 profiler 整理已随 slim 分支移除，可检出 `fp8_tp` 分支查看。

## 6. 结果持久化清单

一次可引用的正式 run 至少包含：

- git commit/dirty 状态、主配置路径与所有覆盖；
- Python/CUDA/driver/vLLM/TK 版本和卡组拓扑；
- `nvidia-smi` 空闲检查与时钟/异常记录；
- warmup、iters、seed、正确性结果和所有 JSON；
- 结果目录 `tp_test_results/tp_run_<时间戳>/`（summary.txt/logs/json/
  clocks_per_step.csv）；
- `HANDOFF.md` 顶部摘要，以及本目录对应主题文档的结论更新。

## 7. 每次运行打印的每 expert token 数

`moe_bench/routing_stats.py`。三个入口（`bench.py` 单卡、`distributed.py` 分布式、
`tools/time_tp_stages.py`）都在 `setup()` 之后、计时之前打印一行，省得事后从 seed
反推这一轮的路由长什么样：

```
[routing] 每 expert token 数 (tktp, E=64, T=512/rank × 4):
  [264, 249, 260, 254, 286, 254, 262, 248, 242, 235, 241, 262, 240, 243, 266, 265,
   ... 共 E 个 ...]
```

- 数的是 (token, expert) **assignment**，不是 token（一个 token 有 TopK 个），
  合计恒为 `world × T × TopK`。
- 分布式下是**全局**口径（一次 all-reduce 合并各 rank 的本地计数）——TP 每张卡
  都要算整批 gathered token，只有全局计数对得上 kernel 真正处理的行数；这个数与
  `tk_tp_scheme` 建表时的 `bincount(all_topk)` 同源。balanced + E=64 下每个都是
  256，`uniform`/`skewed` 的不均衡程度在这里一眼可见（对应
  [09](09_路由不均衡与padding粒度.md) 的 padding 粒度税：每 expert 补齐到
  `ROW_BLOCK=128` 的整数倍）。
- 关闭：`MOE_BENCH_ROUTING_STATS=0`。打印和那次 all-reduce 都在计时区外
  （`setup` 之后、warmup 之前），不进任何测量。开关必须对所有 rank 一致
  （worker 继承父进程环境，天然满足），按 rank 判断会把其余 rank 挂在 all-reduce 上。
