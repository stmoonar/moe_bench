# 04 SM 内组织

> 主题：一个 SM/CTA 内部，通信逻辑放在哪里、warp 怎么分工、寄存器和 shared memory 怎么隔离，才能不伤 GEMM 主路径。

## 1. 第一原则：保住 Tensor Core 主循环

- **不要为了 overlap 把高效 GEMM 拆成很多小 GEMM**：小 GEMM 降低 Tensor Core 利用率、放大 wave 量化、增加 launch 开销。TransformerEngine 式"切成 TP 份小 GEMM + 预留 SM"在 TP=8、小 shape 下崩坏（Flux 对其最大 4.68×），是最重要的反面教材。
- 通信逻辑只允许出现在三个位置：**prologue（读入前等待）、epilogue（写出后信号/远端写）、专职 warp/block**。主循环（MMA 流水）一条指令都不要加。
- 衡量标准：融合后的 GEMM 与纯 GEMM 的 TFLOPS 差距应控制在个位数百分比内；FlashOverlap 的做法（每 tile 只在 epilogue 末尾由 thread 0 做一次原子加）是"最小侵入"的极限形态。

## 2. 等待放在哪个 warp：让 warp specialization 隐藏 spin

- Hopper 的 producer/consumer warpgroup 结构天然适合：**等待收敛到 producer（load）warp**——只有发起 TMA load 的 warp 需要确认数据就绪，consumer warpgroup 只等 mbarrier，不自旋 global flag（Flux 的 AG prologue、Comet 的 fetcher 都是这个结构）。
- persistent kernel 中，同一 CTA 处理多个 tile 时，只在"依赖的 chunk 区间发生变化"时才重新等待——连续 tile 命中同一 chunk 就不重复 spin。
- 自旋要有退避（短暂 nanosleep 级）和上限：无限自旋烧发射槽、干扰同 SM 其他 warp；带超时+陷阱的等待原语（TK 的做法）是调死锁的利器，生产版本保留可配置的超时报警。

## 3. 寄存器与 shared memory 的预算隔离

- **非对称寄存器分配**：producer warp 组降到 ~40 寄存器、consumer 升到 ~232（Hopper 的寄存器重分配机制），给通信/搬运 warp 留最小预算，MMA warp 拿大头——Flux/Comet/TK 全部采用。
- **通信角色复用 smem 而不是另开**：专职通信 CTA 把同一块 smem 按自己的布局重新解释（数据累加区 + 路由索引区）；同 CTA 内的通信 warp 与计算流水共享 smem 环形缓冲的空闲 stage。原则：通信的 smem 需求必须显式声明并静态验证，不能与 GEMM 流水的 stage 数隐性冲突。
- 输出缓冲与输入环重叠布局时，靠编译期断言保证前几个 stage 不会踩到上个任务的输出区（TK 的骨架细节）——smem 复用必须有静态检查兜底。

## 4. pipeline 骨架：producer 是事件循环，天然可挂通信

值得复用的 kernel 骨架心智模型（TK 的 lcsf 模板）：

```text
CTA = producer warp(s) + consumer warpgroup(s)，smem 环形缓冲 + 相位位域
producer 主循环（事件驱动 poll）:
  若 输出槽就绪  -> 发起 store（本地或远端）
  若 输入槽空闲  -> 发起 load（本地或远端，前置 tile 级 wait）
  否则           -> 微睡眠退避
consumer 主循环:
  等输入槽到达 -> MMA/计算 -> 标记输入槽用完 -> 写输出槽
```

- producer 的 poll 循环里"再加一条通信流"（远端 store + 跨卡 signal）是自然扩展——通信发起只是"再多一个单线程 warp 的事"。
- 异步硬件（TMA/mbarrier）自带因果序，同类代理内不需要额外 fence；只有跨代理（异步引擎 vs 普通指令）才补 fence——多余的 fence 会白丢两位数 TFLOPS（TK 2.0 的教训）。
- 发起 TMA 用"选举一个 leader 线程"的写法而不是"lane 0 判断"，让编译器识别单线程意图（小 kernel 有 ~10% 差距）。

## 5. persistent kernel 与任务获取

- 三档任务分配方式，按通信模式的规则程度选择：
  1. **静态跨步**（task_id 从 blockIdx 开始按 grid 跨步递增）：最简单，规则通信（TP、规则 MoE）够用；
  2. **静态指令流**（host 预排好每 SM 的任务序列，device 解码执行 + 双缓冲预取下一条指令）：任务异构但可预排时用；
  3. **集中式 device 调度器**（1 个 OS block 维护任务队列/就绪队列/门铃，动态派发）：只有高度不规则（动态路由 + 到达顺序驱动）才值得，复杂度高一个量级，且调度 block 本身占 1 个 SM、单 warp 调度器可能成为吞吐瓶颈。
- persistent kernel 的占用率陷阱：cluster 尺寸会降低可驻留 SM 数（如 148 SM 的芯片 cluster=4 只能激活 132）；**所有卡的 grid 必须同时可驻留**，任何一张卡少一个 CTA，跨卡自旋就是死锁。上线前验证实际驻留数，不要相信理论 SM 数。

## 6. epilogue 融合的具体纪律

- 信号置位必须在"结果确实落地"之后：先等本 tile 的异步 store 全部完成，再置 flag——顺序颠倒是 silent corruption。
- 远端写（push）用普通 store/TMA 批量写；远端归约用系统级原子加时注意**数据类型支持不一致**（BF16 原子加在旧架构缺失，需退 FP32 且缓冲翻倍）和**非确定性求和顺序**（训练可复现性受影响）。
- 通信后的 elementwise（RMSNorm、residual、量化）尽量融进通信 kernel 的寄存器阶段：数据已在寄存器时顺手算掉，且 RS 分片后计算量除以 world_size（TokenWeave 单项 1.4×）。
- epilogue 里的 gather/scatter 间接寻址会破坏写出连续性——用"重排融进写出地址"的思路（见 02 篇），保持每个通信段地址连续。
