# 07 通信底座与拓扑

> 主题：选什么机制搬数据（四档执行体）、push 还是 pull、单机与跨节点的拓扑策略。

## 1. 通信执行体四档谱系（按 SM 占用从高到低）

| 档位 | 机制 | SM 成本 | 适用 |
|---|---|---|---|
| GPU 线程直读写 | P2P 映射内存上的 load/store/原子（MemoryChannel 类） | 占少量 SM | 节点内、细粒度、需要就地 gather/归约 |
| GPU 发起的批量搬运 | TMA/异步批量拷贝到远端映射地址 | 极低（异步引擎） | tile 级 push/pull 的主力 |
| copy engine / host proxy | stream 拷贝原语、代理线程驱动 CE 或 RDMA | **0 SM**（host 有开销） | 规整大段、AG 分片分发 |
| NIC 后台 / 在网计算 | GPU 发起 RDMA（写完即返回）、NVSwitch 在网归约/多播 | **0 SM / 归约不占 ALU** | 跨节点低延迟；节点内 AllReduce 类 |

原则：**每一档只干下一档干不了的事**。归约能给交换机就给交换机（multimem，通信 SM 直接降到 2~8）；搬运能给 copy engine/NIC 就不用 SM；SM 只保留细粒度控制与含计算的通信（gather、topk 归约）。

## 2. 通信库选型

- **NCCL**：无 device 端可嵌入 API，只能整段 collective——适合作 baseline 和"signal 触发式"低侵入方案（保留其拓扑/协议优化，无 P2P 环境的唯一选择）。注意它默认占 16+ SM，并发时 GEMM 慢 15~20%。
- **NVSHMEM**：对称堆 + device 端 put/get/signal 全集 + GPU 直发 RDMA（IBGDA）；编译器生态（Triton 系）主要绑它。代价：对称堆与框架分配器共存麻烦、按最大 shape 预留显存、分配是集合操作（易死锁）。
- **MSCCL++**：不强制对称堆（任意 buffer 注册）、计数 semaphore、0-SM 的 proxy 通道、LL packet、原生 AMD。样板代码多、生态小。
- **自定义 P2P/IPC**：单机 NVLink 下自己管理对称 buffer + 写值原语，最轻量（Flux 单机路径）。
- **建议**：抽象一层自己的 signal/wait/put 接口，底下可插 NVSHMEM / MSCCL++ / 自定义 IPC——三者的原语语义高度同构（put+signal、计数等待、对称地址），接口层成本低，换底座不改 kernel 逻辑。

## 3. push vs pull

结论先行：**无普适赢家，按拓扑与算子方向 autotune**，但有结构性倾向：

- consumer-wait 型（AG）：push（生产方拷给所有人）与 pull（消费方按需拉）都可行；NVSwitch 下"每 rank 直接从所有 peer 拉"无链式依赖，更稳。
- producer-push 型（RS）：Hopper 上 pull 模式有优势——消费方用 DMA/TMA 从远端拉回再本地归约，读远端不经过本地 L2 的读放大路径，且把归约放在数据归属方；push + 远端原子加则省一跳但受数据类型和原子吞吐限制。
- 跨节点永远是"节点间传输 + 节点内扇出/归约"的两段式，两段可分别选 push/pull。

## 4. 单机拓扑策略

- **NVSwitch/全 NVLink**：all2all 直连（每 rank 同时与所有 peer 交换），swizzle 用 rank 偏移错峰；在网归约（multimem）可用时优先。
- **PCIe（含多 NUMA）**：带宽低、争用敏感——ring 顺序传输（NUMA 内环 + NUMA 间并行）；**GEMM 与通信必须分 kernel 分 stream，且通信 stream 高优先级、GEMM 放低优先级 stream**（通信 CTA 需要抢占能力，Flux 在 PCIe 上与 NVLink 完全相反的部署策略）；通信 CTA 数固定小值（个位数）。
- P2P 能力必须运行时探测并自动降级：消费级 GPU、虚拟化、ACS/IOMMU 都可能禁 P2P；跨卡原子支持要单独探测（不支持就退环形同步模式）。
- 同型号 GPU 也有特例（如某些型号 P2P read 不佳改走 memcpy + 更多拷贝 block）——设备名单独特判在生产库中是常态，框架要留 per-device 覆盖钩子。

## 5. 跨节点拓扑策略（IB + NVLink 协同）

- **两跳转发是核心模式**：跨节点数据只发往目标节点**同 GPU-index** 的 rank（IB 流量最小化、路径规则化），到达后经 NVLink 在节点内扇出给真正的目标 GPU。IB ~50 GB/s 与 NVLink ~160 GB/s 的 3.2× 带宽差决定了这个结构：一份跨节点流量支撑 3 份节点内扇出。
- 配套的算法侧约束：限制每 token 的目标节点数（如 ≤4 节点），使跨节点流量与选中 expert 数解耦。
- 转发链的每一级都是环形队列 + 计数信号，收发/转发/归约由不同 warp 角色承担（见 03/05 篇）。
- 网络工程配套：流量类别用 IB 虚拟通道隔离；重负载开自适应路由；NIC 亲和、rank placement 影响显著。
- 跨节点 AllReduce/RS 优先两级化：节点内先归约（NVLink），节点间只传一份（IB），再节点内广播。

## 6. 对称内存与缓冲管理

- 对称分配是集合操作且通常按最大 shape 预留——动态 shape 场景的显存浪费要预算；中间缓冲的量级参考：中型 MoE 每层几十 MB。
- 通信缓冲与信号缓冲分区管理，生命周期独立于框架分配器（注册制比对称堆灵活）。
- 发送缓冲复用前必须确认在途完成（flush/quiet 语义），双缓冲是最简单的规避。
- 特定 CUDA 版本 + 特定分配方式有已知 driver 问题（如旧版本 NVLink 机器上的对称分配），底座层要有按环境切换分配路径的开关。

## 7. 低延迟路径要单独设计

高吞吐与低延迟是两套不同的最优解，生产库（DeepEP）把它们做成两条独立路径：

- 高吞吐：环形队列、chunk 聚合、两跳转发、20 SM——大 batch 训练/prefill。
- 低延迟：固定上界双缓冲、per-目标 QP、GPU 直发 RDMA、发送/接收两阶段 + 钩子回调（传输期 0 SM）、兼容 CUDA graph——decode 小 batch。
- 决策点：消息大小跨过"带宽曲线拐点"与否；框架应允许运行时按 batch 切换路径，且两条路径切换时缓冲要显式清理。
