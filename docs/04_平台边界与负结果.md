# 平台边界与负结果

本篇记录“不要重复投入”的结论，但这里的“平台”不是 GPU 型号的同义词。除纯代码正确性
bug 外，性能结论都绑定到**具体机器、具体四卡子拓扑、当时的软件栈和工作负载**。归档中的
主要带宽和性能数据来自早期 16 卡服务器及 `9,11,13,15` 等卡组；当前协作环境已是 8 卡机器，
优先卡组为 `0,1,2,3`。两者不能共享未经复测的“本机实测值”。

## 1. 事实的三个层级

| 层级 | 例子 | 换机器后的处理 |
|---|---|---|
| 架构/实现约束 | SM120 指令可用性、同 SKU 的 SM 数、shared-memory 上限、kernel 的内存序要求 | 同 GPU SKU 和编译目标下通常可继承，但仍需 probe/编译确认 |
| 机器/拓扑实测 | P2P 可达性、push/pull/CE 带宽、RTT、远端原子行为、NUMA 干扰 | **必须重新测**；同型号 GPU 也可能不同 |
| 软件栈/工作负载裁决 | `comm_sms=24`、CE/Comet-N 为负、RB64 适用档位、端到端耗时降低 | **必须按主配置重跑 A/B**；不能从旧机器直接带过来 |

会改变后两层结论的因素包括：PCIe 代际和链路宽度、switch/跨 root-complex 路径、
`nvidia-smi topo -m` 的 PIX/PXB/PHB/SYS 关系、NUMA 绑核、ACS/IOMMU、P2P/native atomic
支持、BIOS、driver/CUDA/NCCL、功耗与 boost 时钟、MIG/共享任务以及卡组位置。

### 1.1 历史机器实测基线（待在当前 8 卡机复测）

| 事实 | 历史实测结论 | 作用域 |
|---|---|---|
| GPU 资源 | 110 SM，opt-in shared memory 99KB/block | RTX PRO 5000 SM120 SKU；新机仍需 probe |
| P2P | 测试四卡全通；CE 约 54~56GB/s | 早期服务器及对应卡组 |
| SM push / pull | push 约 50.9GB/s、4 SM 打满；四卡并发 pull 约 23.5GB/s，需更多 SM | 早期服务器四卡子拓扑 |
| PCIe 延迟 | 小写 RTT/每次 wait 约 1.5~2µs | 早期服务器四卡子拓扑 |
| BF16 L0 comm_sms | U 型拐点为 24 | 旧拓扑 + 旧软件栈 + 对应 shape |
| 通算干扰 | L0 GEMM 变慢基本可由 `110/(110-comm_sms)` 的 SM 让渡模型解释 | 对应 kernel/resource 配比 |
| FP8+FP32acc | raw 约 304~311 TFLOP/s，正式版约 283；相对 BF16 耗时降低约 21.9%~25.4% | 同 SKU 上有参考价值，仍受频率/编译器影响 |
| 运行环境 | 共享机器曾有间歇干扰，serial 也出现双峰 | 仅描述当时服务器 |

### 1.2 换机器后的最小重新定标

在复用本篇任何性能裁决前，至少记录并重测：

1. GPU/driver/CUDA/NCCL、功耗/时钟、`nvidia-smi topo -m`、NUMA、P2P access/native atomic；
2. 四卡并发 SM push、SM pull、CE 带宽和小消息 RTT，不只测单对 GPU；
3. BF16/FP8 单卡 grouped GEMM 与 FP8 raw-cap，确认计算侧天花板；
4. 主配置下 `comm_sms` sweep、阶段归因和 serial/tktp 正确性；
5. 若要沿用 CE、Comet-N、push 等负结果，至少重跑对应最小 A/B，而不是只引用旧数字。

结果必须进入新的 `configs/runs/<run>.yaml`。旧值可以作为假设和 sweep 起点，不能作为新机器的
默认定档依据。

## 2. 历史机器上已定案的负结果

| 路线 | 结果 | 根因/适用边界 | 处置 |
|---|---|---|---|
| EP/TP dispatch push 设默认 | 主 shape 无收益或更慢 | L0 已 GEMM-bound；强 push 带宽不在关键路径 | 保留实验路径，默认 pull |
| FP8 后减少 comm_sms | 8/12/16/24 单调到 24 最好 | pull 是 RTT/在飞并发受限，字节减半不减少并发深度 | 旧机默认 24；新机重扫 |
| L1 按 N 维分解（Comet-N） | 修复粒度后仍慢于 v1 | PCIe push 消耗 SM；通信与 GEMM 在 SM 维度零和，提前算完只把 wire 暴露到尾部 | v1 回默认 |
| Copy Engine L0/L1 | L0 +236、L1 +450、双 CE +609µs | CE 编排把 token 消费序流水退化为多 MB 分片搬运 | 代码留档，默认关 |
| schedule 合并 all_gather | 约 +20µs | 省一次 NCCL 启动不及 strided copy 成本 | 不采用 |
| L1 v1 减 comm 预算 | 预算越小越慢 | comm 块是有效推流工，少块喂不满 wire | 旧机保持实测预算；新机重扫 |
| ROW_BLOCK=64 全局默认 | NE≤128 变慢 | 减 padding 同时进入小 tile/小 wave 低效区 | 仅 NE=256 A/B 使用 |
| 独立 torch 量化阶段 | tok_copy 30→112µs | 多个小 kernel 启动和往返 | 单 kernel/epilogue 融合 |
| 远端原子 RMW 计数 | 高并发会丢增量 | 弱压力 probe 曾误判可用 | 禁止用于完成协议 |
| 通信 warp 化（方案A，当前 8 卡机实测） | L0 融合税 +222 vs 默认 +183；L1 +301 vs +173 | **per-SM TMA 队列 HoL**：µs 级 PCIe peer TMA 读在本 SM 队列里堵住 GEMM 流水加载，1 lane/SM 即 +175µs 且随 lane 数单调；gate/straggler 税 ≈0（该假设排除）；warp 几何本身免费 | 代码留档（TK_L0_WARP/TK_L1_WARP 默认 0）；残余方向 = 非 TMA 向量加载绕开队列，见归档 2026-07-16 方案A 文档 |

Copy Engine 的结论不是“CE 永远慢”，而是当前分片方案破坏了消费粒度。若未来能由源端 pack
并按消费 chunk 多流投递，可重新立项，但必须先证明不会退化成大块 barrier。

## 3. FP8 的平台税与正确性边界

SM120 工作站芯片上，E4M3 输入配 FP32 accumulator 的 MMA 指令率没有带来理论
50% 的耗时降低。
去掉 scale 与重标定后的 raw 探针仍只有约 305 TFLOP/s，说明正式 kernel 已接近该路径上限。
FP16 accumulator 虽可能提高吞吐，但 128-K block 内随机游走有真实溢出风险，不采用。

当前 W1 为满足 GLU tile 交织，经历反量化、交织、再量化，产生额外数值误差；历史 rel_err
约 `4.28e-2`。在消除二次量化或正式修改容差之前，FP8 性能与正确性结论必须分开表述。

## 4. 必须记住的正确性与死锁坑

### `group::store` 行映射

8 consumer warp 的 store strip 顺序是 `0,2,4,6,1,3,5,7`，consumer 加载 A 时必须使用
相同的 `local_warpid`。曾经只有前 16 行正确、其余静默错约 6%，并被宽松 max diff 掩盖。
改变 `CONSUMER_WARPS` 后必须重新推导并做逐行对拍。

### named barrier 混用

`__syncthreads()` 使用 barrier 0。TK consumer group 对 barrier 0/1 以 256 线程计数时，
若 288 线程整块同时用 `__syncthreads()`，属于不同 arrival count 并发混用，Blackwell 上表现为
`illegal instruction`。角色汇合必须使用独立 barrier id。

### persistent kernel 饿死辅助 kernel

持久 kernel 占满 110 SM 并等待 flag 时，`cudaMemsetAsync` 或某些同设备 memcpy 可能以小
kernel 实现，无法获得 SM，双方互等即死锁。需要限制 persistent grid，给辅助工作留 SM；
更根本的办法是让依赖操作在 persistent kernel 启动前完成或由其自身执行。

### 默认 device 污染 host 表

worker 调用 `torch.set_default_device(cuda)` 后，未显式 `device="cpu"` 的 host 调度临时 tensor
会落到 GPU：可能直接设备混用，也可能退化成数万次单元素 GPU 写。host builder 的每个创建点
都必须显式指定 CPU。

### 构建正本

`kernels/tk/sm120_common.cuh` 会在编译前被覆盖且被忽略；修改它不会进入 Git。必须修改
`kernels/tileoverlap/common/sm120_common.cuh`。切换编译期 world size/row block 时也要确认
缓存 key 或 clean build，避免旧 `.so` 静默复用。

## 5. 负结果的复用原则

每次重新打开已冻结路线前，必须写出“哪个前提已经改变”。有效的新前提例如 NVLink/NVLS、
通信不占 SM 的细粒度引擎、更大的 token 批量或不同消费顺序；仅仅换参数再跑一次不构成重新
立项的理由。原始证据见归档 08、10、16、25、31~35、38~45。
